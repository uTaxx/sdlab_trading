# Stock Trading System — Developer Handover

작성일 2026-08-31. 대상은 이 시스템을 이어받아 개발할 사람이다.

**이 문서의 원칙.** 지금 코드에 실제로 구현된 것만 적는다. 의도와 구현이
다르면 나눠서 적는다. 코드로 확인하지 못한 것은 `확인 필요`라고 표시한다.
추측해서 채우지 않는다.

**작성자가 확인한 방법.** 각 절의 사실은 해당 파일을 직접 열어 읽고 적었다.
파일 경로와 줄 번호를 같이 남겼으니 의심되면 그 자리를 보면 된다. 실제
매매 기록은 2026-08-31 23:26에 운영 DB를 읽어서 얻었다.

## 1. Executive Summary

한국 주식 자동매매 시스템이다. 한국투자증권(KIS) **모의투자** 계좌에만
연결돼 있고, 실제 돈이 나가는 거래는 한 번도 하지 않았다.

| 항목 | 값 |
|---|---|
| 언어 | Python 3.11 |
| 소스 | `src/muwon` 109파일 19,935줄 |
| 스크립트 | `scripts/` 39파일 7,823줄 |
| 테스트 | `tests/` 93파일 14,781줄, 1,201건 전부 통과 |
| 자동화 | GitHub Actions 27개 워크플로 |
| 스케줄러 | n8n (외부 SaaS) |
| 설정 저장소 | 구글 시트 |
| 상태 저장소 | 구글드라이브의 SQLite 파일 하나 (`muwon.db`) |
| 시세 | 야후 파이낸스 (백테스트·신호), KIS API (주문·잔고) |
| 화면 | 정적 HTML + n8n webhook (GitHub Pages) |

**지금 실제로 도는 하루.** 08:30에 매수 후보를 뽑아 텔레그램으로 승인을
요청한다. 사람이 구글 시트에 체크하거나 텔레그램 버튼을 누른다. 09:05에
승인된 것만 산다. 장중 5분마다 손절선을 본다. 17:30에 실제 체결로 기록을
맞추고 17:40에 시트에 남긴다.

**사람이 승인하지 않으면 아무것도 사지 않는다.**

### 실거래로 넘어가기 전에 반드시 알아야 할 세 가지

1. 백테스트 유니버스와 실제 매매 유니버스가 **다르다.** 4절을 볼 것.
2. 슬리피지를 **한 번도 재지 않았다.** 모든 백테스트가 슬리피지 0 가정 위에 있다.
3. 생존 편향이 **제거되지 않았다.** 7절을 볼 것.

### 2-4. 데이터 흐름 (백테스트)

```
[Yahoo Finance API]
        │
        ▼
[PriceCache]
        │
        ▼
[load_histories]  유니버스 전체를 한 번에 받음
        │
        ▼
[add_indicators]  이동평균·RSI·MACD 등을 미리 계산해 붙임
        │
        ▼
[BacktestEngine.run]  날짜 순으로 하루씩
        │   0)  전날 정한 매도를 오늘 시가에 체결 (exit_at_open일 때)
        │   0b) 전날 정한 매수를 오늘 시가에 체결 (entry_at_open일 때)
        │   1)  청산 판단 (오늘 종가로)
        │   2)  평가금액 계산 → 오늘 손익률
        │   3)  진입 판단 (오늘 종가로)
        │   4)  평가금액 기록
        ▼
[BacktestResult]  equity_curve + closed_trades + final_positions
        │
        ▼
[compute_metrics]  수익률·MDD·Sharpe·승률·손익비 등
```

**실거래와 백테스트가 공유하지 않는 것.** 두 경로는 전략(`strategy/`)과
리스크 정책(`risk/`)과 지표(`indicators/`)를 공유하지만, 루프 자체는
`backtest/engine.py`와 `execution/engine.py`로 따로 있다. 같은 규칙이
양쪽에 두 벌로 적혀 있다는 뜻이다.

## 3. Data Pipeline

### 3-1. 시세 수집

| 항목 | 실제 구현 |
|---|---|
| 제공처 | 야후 파이낸스 `query1.finance.yahoo.com/v8/finance/chart/{symbol}` |
| 파일 | `src/muwon/data/yahoo_client.py` |
| 티커 형식 | `005930.KS`(코스피) / `247540.KQ`(코스닥) |
| 받는 값 | `indicators.quote[0]` 의 open/high/low/close/volume |
| 주기 | 스크립트가 실행될 때마다. 상시 수집 없음 |
| 저장 | `.cache/prices.sqlite` (SQLite). GitHub Actions 캐시로 실행 간 재사용 |
| 재시도 | 3회 (`RETRIES = 3`, `price_cache.py:41`) |

**수정주가 여부.** 코드는 `quote` 배열을 쓰고 `adjclose` 배열을 쓰지 않는다
(`yahoo_client.py:55-68`). 야후의 `quote`는 통상 액면분할은 반영하고 배당은
반영하지 않는다. 즉 **배당은 수익률에 안 들어간다.**

액면분할 반영은 야후에 의존하는데, 최소 한 종목에서 안 된 것을 확인했다.
주성엔지니어링(036930)의 5년 시세에 하루 52.6% 변동이 있다. 한국 증시는
하루 등락이 ±30%로 제한되므로 이 값은 자료 오류다.

### 3-2. 결측·오류 처리

| 상황 | 실제 구현 |
|---|---|
| 종가가 NaN | 그 줄을 버린다 (`yahoo_client.py:68` `dropna(subset=["close"])`) |
| 시세를 못 받음 | 그 종목만 건너뛰고 나머지는 진행 (`propose_buys.py:129-136`) |
| 최소 일수 미달 | `최소일수` 인자로 걸러 냄 |
| 거래정지 | **처리 코드 없음.** 검색해도 안 나온다 |
| 상장폐지 | **처리 코드 없음.** 주석에 언급만 있고 로직은 없다 |
| 신규상장 | 시세가 시작되는 날부터 자동으로 들어간다. 별도 처리 없음 |
| 액면분할·병합 | **처리 코드 없음.** 야후가 준 값을 그대로 쓴다 |
| 배당 | **반영 안 됨** |

### 3-3. 데이터 검증

- `scripts/verify_sector_catalog.py` 가 종목 코드와 20일 평균 거래대금을 확인한다.
  거래대금이 문턱 미만이면 경고한다. 자동으로 끄지는 않는다.
- 그 밖의 시세 자체에 대한 자동 검증은 **없다.** 하루 등락이 ±30%를 넘는지,
  가격이 0인지, 날짜가 빠졌는지 확인하는 코드가 없다.

### 3-4. 확인된 데이터 오류 목록

| 종목 | 증상 | 상태 |
|---|---|---|
| 036930 주성엔지니어링 | 하루 52.6% 변동. 한국 증시 제한 초과 | 안 고침 |

**확인 필요:** 나머지 62종목은 하루 최대 변동이 30% 이하인 것만 확인했다.
결측일, 0원, 날짜 역전 등은 확인하지 않았다.

## 4. Universe

### 4-1. 두 갈래가 있다

이 시스템에는 종목 목록이 **두 개** 있고 서로 다르다.

| 목록 | 만드는 곳 | 쓰는 곳 | 크기 |
|---|---|---|---|
| 시가총액 상위 | KIS 시가총액 순위 API → DB 스냅샷 | `run_paper_trading.py`, 기간평가 기본값 | 30종목 |
| 섹터 카탈로그 | 손으로 고른 목록 → 구글 시트 | **`propose_buys.py`** (실제 매수 후보) | 80종목 중 63 거래 가능 |

### 4-2. 문제: 백테스트와 실제 매매가 다른 목록을 봤다

**왜 발생했는가.** 시스템이 두 단계로 자랐다. 처음에는 시가총액 상위 목록

## 5. Strategy

### 5-1. 지금 걸린 전략

`volume_surge_5d_ma20` (화면 이름: 거래량 급증 + 20일선)
구현: `src/muwon/strategy/breakout.py` `VolumeSurgeStrategy`

파라미터 (`VolumeSurgeParams`, `breakout.py:85-97`):

| 이름 | 값 | 뜻 |
|---|---|---|
| `volume_ma_window` | 20 | 거래량 평균을 낼 일수 |
| `volume_surge_ratio` | 2.0 | 거래량이 평균의 몇 배여야 하나 |
| `min_price_change_pct` | 2.0 | 그날 최소 상승률(%) |
| `sma_short` | 20 | 이동평균 일수 |
| `holding_days` | 5 | 이 일수가 지나면 청산 |
| `exit_sma` | 20 | 이 이동평균 아래로 내려오면 매도 신호 |

### 5-2. 매수·매도 조건

| 항목 | 설계 의도 | 실제 구현 |
|---|---|---|
| 매수 조건 | 거래량이 늘고 값이 오르며 추세 위일 때 산다 | 거래량 ≥ 20일 평균 × 2.0 **그리고** 종가 전일 대비 ≥ +2.0% **그리고** 종가 > 20일 이동평균. 셋 다 만족해야 BUY 신호 |
| 매도 조건 | 추세가 깨지면 판다 | 종가 < 20일 이동평균이면 SELL 신호 |
| 신호 우선순위 | 매도가 먼저 | 같은 날 두 신호가 다 서면 매도가 먼저 (`breakout.py:137-139` 주석) |

**중요.** 매수 조건과 매도 조건은 서로 다르다. "매도 전략이 매수와 같다"는
표현은 같은 전략 객체가 둘을 다 낸다는 뜻이지 조건이 같다는 뜻이 아니다.

### 5-3. 청산 규칙 (실거래·백테스트 공통)

`src/muwon/risk/exits.py` `evaluate_exit()`가 판단하고, 두 엔진이 같이 쓴다.

순서는 이렇다.

1. **ATR 손절** — `atr_stop_enabled`가 켜져 있고 ATR을 구할 수 있으면.
   지금 설정은 꺼짐.
2. **고정 손절** — 수익률 ≤ `stop_loss_pct`. 지금 -5%.
3. **익절** — 수익률 ≥ `take_profit_pct`. 지금 0이라 꺼짐.
4. **트레일링 스톱** — `trailing_stop_enabled` 켜졌을 때. 지금 꺼짐.
5. **보유 기간** — `exits.py` 밖에서 처리. `max_holding_days`가 0이면
   전략이 정한 값(5일), 0이 아니면 그 값으로 덮어쓴다.
6. **전략 매도 신호** — 위 어느 것도 아니면.

### 5-4. 항목별 설계 의도와 실제 구현

| 항목 | 설계 의도 | 실제 구현 | 코드 위치 |
|---|---|---|---|
| 손절 | 종목 성격에 맞춰 ATR로 | **고정 -5%.** ATR 손절은 코드가 있으나 꺼져 있음 | `exits.py:88-94` |

## 7. Backtest Engine

파일: `src/muwon/backtest/engine.py` (약 440줄)

### 7-1. 시점과 가격

| 항목 | 실제 구현 |
|---|---|
| 매수 신호 시점 | 그날 종가 기준으로 계산. 루프의 3번 단계 |
| 실제 매수가 | `entry_at_open=False`(기본): **그날 종가**<br>`entry_at_open=True`: **다음 날 시가** |
| 매도 신호 시점 | 그날 종가 기준. 루프의 1번 단계 |
| 실제 매도가 | `exit_at_open=False`(기본): **그날 종가**<br>`exit_at_open=True`: **다음 날 시가** |
| 수량 결정 시점 | 체결 시점의 평가금액으로 (`engine.py:210-217`) |

**실거래와 맞추려면 `entry_at_open=True, exit_at_open=True`가 맞다.**
실거래 엔진은 어제까지의 완성된 일봉으로 판단하고 개장 직후 시장가로 낸다.

기간평가(`run_period_check.py`)는 두 옵션을 켜고 돈다. `experiment.yml`의
`fill_timing` 기본값은 `close`라 안 켜져 있다.

### 7-2. 비용

`src/muwon/backtest/costs.py`

| 항목 | 값 |
|---|---|
| 매수 수수료 | 0.015% |
| 매도 수수료 | 0.015% |
| 매도 증권거래세 | 0.18% |
| 슬리피지 | **0.0** |

주석에 실제 크기 추정이 적혀 있다. 6만원 종목의 호가 단위가 100원이라
한 칸이 0.17%, 반호가만 잡아도 편도 0.08%. 값을 0으로 둔 이유는 과거
결과와 비교하기 위해서다.

### 7-3. 가정과 미구현

| 항목 | 실제 구현 |
|---|---|
| 호가/체결 가정 | 원하는 수량이 종가(또는 시가)에 **전량 체결**된다고 본다 |
| 거래량 제한 | **없음.** 하루 거래량의 몇 %까지만 산다는 제약이 없다 |
| 부분 체결 | **없음** |
| 거래정지 | **처리 없음.** 시세가 있으면 거래한다 |
| 상장폐지 | **처리 없음** |
| 신규상장 | 시세 시작일부터 자동 포함 |
| 액면분할·병합 | **처리 없음.** 야후 값을 그대로 씀 |
| 배당 | **반영 안 됨** |
| 결측 데이터 | 종가 NaN이면 그 줄을 버림. 보유 중 시세가 없는 날은 마지막 종가를 이어 씀 |
| 데이터 수정 | 안 함 |

### 7-4. 편향

**Look-ahead bias.** 없는 것으로 보인다. 근거는 셋이다.

- 신호는 `MarketContext(as_of=current_date)`로 그날까지의 자료만 본다.
- 섹터 강도는 `_강도()`에서 `기준일 이하`로 자른다 (`sector/selection.py:66-67`).
- 지표는 rolling 계산이라 미래를 안 본다.

**확인 필요:** 전략 27개 각각의 `generate_signals`가 미래 자료를 안 보는지는
전수로 확인하지 않았다. `volume_surge` 계열만 읽었다.

**Survivorship bias.** **있다. 크다.**

유니버스가 "지금" 기준 목록이다. 시가총액 상위 30종목이든 섹터 카탈로그
80종목이든, 오늘 살아남아 있는 회사들이다. 그 목록을 5년 전으로 가져가
돌린다. 5년 전에 있다가 사라진 회사, 순위에서 밀린 회사는 목록에 없다.

`scripts/verify_sector_rotation.py:17-18`에 같은 경고가 적혀 있다.

**Universe leakage.** 있다. 위와 같은 원인이다. 섹터 지수도 오늘의 종목
목록으로 과거를 계산한다.

### 7-5. 현재 백테스트 결과를 믿어도 되는가

**절대 수익률은 믿으면 안 된다.** 이유가 넷이다.

1. 생존 편향이 제거되지 않았다. 수익률이 부풀려진다.
2. 슬리피지가 0이다. 거래가 잦은 전략일수록 과대평가된다.
   5년 1,249건 거래에 편도 0.08%만 넣어도 약 200%p가 깎인다.
3. 배당이 빠져 있다. 이쪽은 반대로 과소평가 방향이다.
4. 성적표(`docs/전략평가.json`)는 실제로 사지 않는 종목 목록으로 잰 것이다.

**순위 비교에는 쓸 수 있다.** 편향이 모든 전략에 똑같이 걸리므로,
같은 조건에서 어느 전략이 나았는지는 비교할 수 있다.

**최대 하락폭(MDD)은 상대적으로 믿을 만하다.** 생존 편향은 수익률을
부풀리지 방향을 바꾸지는 않고, 하락폭은 슬리피지에 덜 민감하다.

## 8. Live Trading Engine

파일: `src/muwon/execution/engine.py`

### 8-1. 판단 근거

`run_once()`는 **어제까지의 완성된 일봉**만 쓴다 (`engine.py:325`
`df = df[df["trade_date"] < trade_date]`). 오늘 봉은 장이 안 끝나 종가도
거래량도 확정이 아니기 때문이다.

### 8-2. 실행 순서

1. 킬스위치 확인 (시트와 DB가 **둘 다** 켜져야 함)
2. 오늘 승인된 종목 읽기
3. 실제 계좌와 DB 대조 (다르면 알리고 진행)
4. 유니버스 = 승인된 것 ∪ 보유 중 (보유를 빼면 손절이 멈추므로)
5. 청산 판단 → 매도 주문
6. 평가금액 재계산
7. 진입 판단 → 리스크 승인 → 수량 결정 → 매수 주문

### 8-3. 주문

| 항목 | 값 |
|---|---|
| 주문 유형 | 시장가 (`ORD_DVSN="01"`, `ORD_UNPR="0"`) |
| 매수 수량 | min(평가금액 × 15% ÷ 가격, 증권사 매수가능수량) |
| 매도 수량 | 보유 전량 |
| 부분 체결 | 체결 수량을 따로 기록하고 알림에 표시 |

### 8-4. 장중 손절 감시

`scripts/watch_stops.py`가 5분마다 돈다. 손절·익절·트레일링만 본다.
매수 판단과 보유기간 만료, 매도 신호는 **하지 않는다.** 완성된 일봉이
있어야 하기 때문이다.

## 15. Environment & Deployment

### 15-1. 로컬 개발

```bash
python3.11 -m venv .venv
.venv/bin/pip install -e ".[dev,cloud]"
.venv/bin/python -m pytest -q          # 1,201건
.venv/bin/python -m ruff check .
```

`.env` 파일에 `DATABASE_URL`과 `MUWON_MASTER_KEY`가 필요하다.
`requirements.txt`는 Streamlit Cloud 배포 전용이고 로컬은 `pyproject.toml`을 쓴다.

### 15-2. 실행 환경

- **연산**: GitHub Actions (ubuntu-latest, Python 3.11). 상시 서버 없음
- **스케줄**: n8n Cloud가 `workflow_dispatch`로 호출.
  GitHub의 `schedule:` cron은 늦어서 안 씀
- **상태**: 구글드라이브의 `muwon.db`. 실행마다 내려받고 끝에 올림
- **화면**: GitHub Pages (`utaxx/sdlab_trading`). 정적 파일이고 데이터는
  n8n webhook으로 받음

### 15-3. 필요한 Secrets

이름만 적는다. 값은 이 패키지에 없다.

`GDRIVE_SA_KEY_JSON`, `GDRIVE_FOLDER_ID`, `MUWON_MASTER_KEY`,
KIS 앱키·시크릿·계좌번호(암호화되어 DB에), 텔레그램 봇 토큰·챗ID(DB에).

대시보드 접속 열쇠는 구글 시트 `설정` 탭의 `dashboard_key` 칸에 있다.
n8n 창구가 요청마다 그 칸을 읽어서 대조한다. 칸이 비어 있거나 시트를
못 읽으면 「맞는 열쇠 찾기」 노드에 적어 둔 옛 값으로 돌아간다.
2026-09-01 이전에는 값이 노드 안에 박혀 있었고 저장소 문서 세 곳에도
평문으로 적혀 있었다. 지금은 저장소 어디에도 없다.
