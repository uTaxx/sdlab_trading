# 화면 하나로 모은다 (2026-08-24 밤)

## 왜 다시 만드나

관리 지점이 다섯이었다. 스트림릿(전략·기준), 구글 시트(승인·기록),
텔레그램(알림·버튼), n8n 화면(지금 손익), GitHub(실행 기록).

**이건 설계가 아니라 누적이다.** 필요할 때마다 하나씩 붙였고, 걷어내기로
한 것(스트림릿)을 안 걷어냈다. "관리를 여기저기 들어가서 하라는 건지"라는
말이 정확한 진단이다.

목표는 **둘**이다. 화면 하나와 텔레그램 알림.

| 지금 | 옮겨 갈 곳 |
|---|---|
| 스트림릿: 전략·기준·킬스위치 | **대시보드 「전략과 기준」 탭** |
| 시트: 승인 칸 | **대시보드 「오늘 승인」 탭** (텔레그램 버튼도 그대로 둔다) |
| 시트: 매매기록·성적 | **대시보드 「기록」 탭** (원본은 시트에 계속 쌓인다) |
| n8n 화면: 지금 손익 | **대시보드 「지금 손익」 탭** |

시트는 **기록 보관과 감사용으로 뒤로 물러난다.** 지우지 않는다. 사람이
직접 열어 확인할 수 있다는 것이 이 시스템의 안전장치 중 하나다.

## 웹훅 규약

화면은 상태를 안 들고 있다. 열 때마다 물어보고 그린다.

### 이미 도는 것

```
POST {n8n}/webhook/muwon-balance   { 열쇠 }
  → { 현금, 순자산, 원가, 평가손익, 조회시각, 종목: [...] }
```

### 새로 만들 것: 창구 하나로 모은다

```
POST {n8n}/webhook/sdlab   { 열쇠, 무엇, ...인자 }
```

**왜 하나인가**: 열쇠 검사도, 허용 출처도 한 곳에서만 보면 된다. 여럿으로
나누면 하나를 빠뜨리고 **빠뜨린 줄도 모른다.** 지금 계좌조회 웹훅의 허용
출처가 옛 주소로 남아 있던 것이 정확히 그 사고였다.

| `무엇` | 인자 | 돌려줄 것 | 상태 |
|---|---|---|---|
| `승인목록` | — | `{ 날짜, 후보: [{종목코드, 종목명, 섹터, 수량, 예상가, 승인}] }` | 됨 |
| `승인` | `종목코드`, `값`(`"Y"`\|`"N"`) | `{ 저장됨, 종목코드, 값, 갱신된칸 }` | 됨 |
| `기록` | — | `{ 승률, 손익비, 최대낙폭, 낙폭기준, 거래: [...] }` | 됨 |
| `기준` | — | `{ 매매켜짐, 매도켜짐, 전략, 매도전략, 손절, 익절, 비중, 동시보유, 읽기만하는칸, 아직없는칸 }` | 됨 |
| `기준저장` | `바꿀것: {...}` | `{ 저장됨, 바꾼칸, 못한칸, 갱신된칸 }` | 됨 |
| `최근주문` | — | `{ 주문: [{때, 종목, 사고팜, 수량, 값, 상태}] }` | 됨 |
| `실행기록` | — | `{ 회차: [{때, 살펴본종목, 매수신호, 매도신호, 주문수, 막힌이유}] }` | 됨 |
| `알림` | — | `{ 알림: [{때, 종류, 글}] }` | 됨 |
| `변경이력` | — | `{ 이력: [{때, 무엇, 이전, 이후}] }` | 됨 |

실패는 전부 `{ "오류": "사람이 읽을 문장" }` 로 돌려준다. **HTTP 200에
오류를 담아도 화면이 알아듣는다**. KIS가 그렇게 답하기 때문에 이미 그
모양을 다루고 있다.

### 못 주는 것은 못 준다고 답한다

화면에 뜰 수 있는 상태는 셋이고, 셋을 섞으면 안 된다.

| 상태 | 뜻 | 화면 |
|---|---|---|
| 진짜 자료 | 창구가 답했고 내용이 있다 | 표를 그린다 |
| 아직 비었음 | 창구가 답했는데 아직 아무 일도 없었다 | "아직 없습니다" |
| 아직 연결 안 됨 | 창구가 이 표를 못 준다 | 왜 못 주는지 적는다 |

뒤의 둘을 같은 빈 표로 그리면 **"아직 아무것도 안 샀다"와 "산 것을 볼 수가
없다"가 구별되지 않는다.** 뒤쪽이 훨씬 나쁘다. 손해가 나 있는데 화면은
조용한 상태가 그것이다. 그래서 창구는 `{ 아직없음: true, 까닭 }`을 돌려주고
화면은 예시를 그리지 않는다.

탭이 아직 안 만들어진 경우가 그 셋째 상태다. 시트의 탭은 첫 줄이 쓰일 때
만들어지므로, 청산이 끝난 매매가 0건이면 `매매기록` 탭 자체가 없다. 그때
창구는 `{ 아직없음: true, 까닭 }`을 돌려주고 까닭에 언제 생기는지를 적는다.

**전략은 보여 주기만 한다.** 지금 어떤 전략이 걸려 있는지는 `muwon.db`
(`strategy.active_keys`)에 있고, 저녁 17:40 올리기가 그것을 `설정!strategy`로
옮겨 적는다. 창구는 시트의 그 값을 읽어 돌려주고 `읽기만하는칸: ["전략"]`을
같이 붙인다. 화면은 "여기서는 못 바꿉니다"라고 적는다. 고르고 저장했는데
아무 일도 안 일어나는 것이 제일 나쁘다.

**파는 쪽을 따로 걸었으면 `매도전략`에 그 키가 온다**(`설정!sell_strategy`).
비어 있으면 사는 쪽 전략이 양쪽을 다 맡고 있다는 뜻이다. 이 칸이 없으면
화면에는 사는 쪽 전략만 뜨고, 실제로는 다른 규칙으로 팔고 있어도 그 사실이
어디에도 안 보인다. 그래서 따로 걸린 경우에는 화면이 알림 상자를 띄운다.

## n8n에 만든 것: 워크플로 `wj3pZvpHJPekTaoI`

이름은 `무원406 대시보드 자료`다. 계좌조회(`Ew7CMMjSThC1E42B`)와 **따로
두었다.** 한 워크플로에 웹훅이 여럿이면 시험 실행이 첫 웹훅으로만 들어가서
나머지를 확인할 방법이 없다. 실제로 그래서 한 번 헛돌았다.

```
Webhook(POST /webhook/sdlab, allowedOrigins: *, responseMode: responseNode)
  → Code 「무엇을 물었나」   열쇠·무엇·갈래(읽기/쓰기)·읽을 범위를 정한다

      └ (오류) → Code「시트 탭이 없음」 → 왜 없는지 적어 응답
  → IF  「쓰는 요청인가」
      ├ 예  → Code「고칠 칸 정하기」 → IF「고칠 게 있나」
      │        → HTTP「시트에 쓰기」 values:batchUpdate → Code「쓴 결과」
      └ 아니오 → Code「화면 모양으로」
  → 「자료 돌려주기」
```

**요청마다 탭 하나만 읽는다.** 세 탭을 한 번에 읽었더니 `매매기록` 탭이

청산이 끝난 매매가 0건이면 그 탭은 존재하지 않는다.

**판단은 여기서 하지 않는다.** n8n은 시트를 읽고 쓰는 것까지다. 무엇이
유효한 승인인지(빈 칸은 거부, 어제 승인은 무효, 목록 밖은 무시)는
`src/muwon/cloud/approval.py`가 정하고, 그 규칙은 매수하는 쪽에서 돈다.

## 켜기 전에 사람이 할 것: 하나뿐

**Settings → Pages → Source 를 `GitHub Actions`로.**

이 저장소는 Pages 자리가 비어 있으므로 다른 화면을 밀어내지 않는다.

> 이건 내가 못 켠다. GitHub 연동에 Pages 설정 권한이 없다. 같은 이유로
> 저장소 만들기도 403이었다.

### 0초 만에 실패하고 로그가 없다면: 워크플로 파일부터 의심한다

첫 배포 둘(#1·#2)이 **0초 만에, 잡이 하나도 안 잡힌 채** 실패했다.
클릭해 들어가도 로그가 없다.

**나는 이걸 "Pages를 안 켜서"라고 단정하고 여기 그렇게 적었다. 틀렸다.**

진짜 원인은 워크플로 파일이었다.

```yaml
- id: 배포                                  # ← 한글 id
  url: ${{ steps.배포.outputs.page_url }}    # ← 그걸 참조
```

**GitHub Actions 표현식 파서는 한글 식별자를 못 읽는다.** 파일이 통째로
파싱에 실패해서 잡이 배정조차 안 됐다.

```
(Line: 43, Col: 12): Unexpected symbol: '배포'
```

이 오류는 **Actions 화면에 안 나온다.** API로 워크플로를 실행해 보고서야
나왔다. 화면에서는 Pages 미설정과 겉모습이 완전히 똑같다.

**교훈**: `id`와 표현식은 영문으로 둔다. 사람이 읽는 `name:`은 한글 그대로
둬도 된다. 파서를 타지 않는 자리다.

그리고 **0초 실패는 "환경 문제"가 아니라 "파일이 안 읽힌다"부터 본다.**
잡이 안 잡혔다는 것은 GitHub이 그 파일로 무엇을 해야 할지 몰랐다는 뜻이다.

### 표마다 조심한 것

- **비밀값은 시트에 안 적는다.** 토큰과 API 키가 변경 이력 같은 표에 있고,
  시트는 사람이 열어 보는 곳이다. 무엇이 언제 바뀌었다는 사실만 남긴다.
- **안 바뀐 줄은 변경 이력이 아니다.** 워크플로가 돌 때마다 같은 자격증명을
  다시 써 넣어서, 처음 올렸을 때 106줄 중 100줄이 `(비밀값) → (비밀값)`
  이었다. 안 바뀐 줄과 기계가 매번 다시 적는 값(토큰, 만료 시각, 텔레그램
  오프셋)을 뺀다. 이미 시트에 쌓인 줄은 지우지 않고 화면에 낼 때만 거른다.
- **주문의 값이 진짜 체결가인지 구분한다.** 체결 / 값 미확인 / 기록 전.
  조회에 실패해 기준가를 적어 놓고 "체결"이라고 하면 슬리피지 통계에
  차이 0인 가짜 표본이 섞인다.
- **알림 표를 DB에 따로 두지 않는다.** 주문·매매·회차에서 그때그때 만든다.
  원본이 둘이 되면 어느 쪽이 맞는지 알 수 없는 날이 온다.
- **쓰는 전략은 읽기만 된다.** `설정!strategy`는 정책필드가 비어 있어서
  무엇으로 바뀌어도 주문에 영향이 없다. 매일 DB 값을 옮겨 적기만 한다.
  전략을 바꾸는 것은 실제 주문에 직접 영향을 주는 결정이라 화면에서 조용히 되게 두지 않는다.

### 화면을 고칠 때 확인하는 법

테스트와 ruff를 통과하고도 화면이 죽은 적이 여러 번 있다. 브라우저로 직접
본다.

```
python3 -m http.server 8899 --directory .
# 그리고 Playwright + /opt/pw-browsers/chromium 으로 1280px와 390px 둘 다
```

**킬스위치 단추는 `confirm()`을 띄운다.** headless에서 그냥 클릭하면 거기서
멈춘다. `page.on("dialog", ...)`로 받아 주지 않으면 확인이 통째로 시간 초과로
끝나는데, 그 실패는 "화면이 느리다"처럼 보여서 원인을 한참 못 찾는다.
