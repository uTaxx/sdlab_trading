# 2026-08-25 — 초록불 아래에서 조용히 죽어 있던 것 둘

같은 날 두 번째 사고 기록이다. 첫 번째(`사고_2026-08-25_유령보유.md`)는
**내가 만든** 사고였고, 이건 **엿새 동안 아무도 못 본** 사고다.

## 무엇이 망가져 있었나

두 스크립트가 설정 객체를 잘못 만들고 있었다.

```python
service = SettingsService(session_factory)   # 틀렸다
service = build_settings_service()           # 맞다
```

사이에 `SettingsStore`가 있어야 하고, 그게 비밀값(KIS 앱키·텔레그램 토큰)을
푸는 열쇠를 들고 있다. 생성은 **조용히 지나가고**, 한참 뒤 첫 읽기에서
터진다.

```
AttributeError: 'sessionmaker' object has no attribute 'get'
```

무엇을 잘못 넘겼는지가 안 보이는 자리에서 터진다.

## 얼마나 오래

| | 첫 실패 | 실패 횟수 | 워크플로 표시 |
|---|---|---|---|
| 30분봉 수집 | 2026-08-20 | **7/7** | 🔴 빨간불 |
| 시장·섹터 리포트 | 2026-08-19 | **8/8** | 🟢 **초록불** |

## 왜 엿새나 못 봤나

### 30분봉 — 진짜 원인이 두 번째 오류에 묻혔다

빨간불이었으니 보이긴 했다. 그런데 **메일에 찍힌 오류가 진짜 오류가
아니었다.**

수집이 실패하면 `intraday.db`가 안 만들어진다. 그런데 뒤따르는 업로드
단계에 `if: always()`가 붙어 있어서, 없는 파일을 올리려다 또 죽는다.

```
FileNotFoundError: [Errno 2] No such file or directory: './intraday.db'
```

로그 맨 아래에 남는 것도, 메일에 찍히는 것도 이것이다. 진짜 원인은 그 위
40줄쯤에 묻혀 있었다. **두 번째 오류가 첫 번째 오류를 가렸다.**

### 시장 리포트 — 실패를 `try/except`가 삼켰다

```python
try:
    TelegramNotifier(서비스).send(요약)
except Exception as e:   # 알림 실패가 리포트를 죽이면 안 된다
    print(f"텔레그램 전송 실패: {e}", file=sys.stderr)
```

의도는 옳다. 텔레그램이 잠깐 안 되는 것 때문에 리포트가 통째로 날아가면
안 된다. 문제는 **네트워크 실패와 프로그래밍 오류를 같이 삼켰다**는 것이다.

결과: 워크플로는 여덟 번 다 초록불, 리포트는 폰에 **한 번도 안 옴.**
"어제 리포트 안 왔네"를 알아채려면 안 온 것을 기억해야 하는데, 원래
조용한 날이 많은 시스템이라 그 기억이 안 남는다.

## 무엇을 잃었나

**엿새치 30분봉은 영영 못 받는다.** 한국투자증권은 국내주식 분봉을
**당일치만** 준다. 08-20, 21, 24 (22·23은 주말)의 장중 데이터는 없다.

장중 모멘텀(첫 30분이 마지막 30분을 예측한다 — 우리가 조사한 단타 후보 중
한국 시장 증거가 있는 유일한 것)을 재려면 약 120거래일이 필요하다. 그
셈이 사흘 늦어졌다.

리포트 쪽은 잃은 게 없다. 아티팩트에 다 남아 있다 — 다만 아무도 안 봤다.

## 고친 것

1. **두 곳 다 `build_settings_service()`로.**

2. **`SettingsService.__init__`에 문지기.** `get`/`set`이 없는 것을 주면
   만들 때 바로 `TypeError`를 내고 *"build_settings_service()를 쓰세요"*
   까지 말한다. 다섯 겹 아래에서 터지면 무엇을 잘못 넘겼는지가 안 보인다.

3. **`market_report`는 텔레그램을 못 보내면 종료 코드 1.** 보내라고 했는데
   못 보냈으면 그건 실패다. 리포트 자체는 다 만들고 아티팩트도 남긴다
   (`if: always()`) — 폰으로 못 받은 날일수록 거기서 읽을 수 있어야 한다.

4. **업로드 단계는 파일이 없으면 경고만 남기고 건너뛴다.** 두 번째 오류가
   첫 번째 오류를 가리는 것을 막는다.

## 확인

2026-08-25 16:43 KST, 고친 뒤 손으로 돌렸다.

```
390칸 저장했습니다.
■ 2026-08-25 수집 결과
  30종목 × 13칸 = 390칸 중 **390칸** (100.0%)
  빠진 칸 없음.
지금까지 1거래일치가 쌓였습니다 (2026-08-25 ~ 2026-08-25).
```

시장 리포트도 같은 시각에 돌려 텔레그램이 실제로 나갔다.

**그 자리에서 알게 된 것: 장 마감(15:30) 뒤에도 당일 분봉은 받을 수 있다.**
16:43에 100%를 받았다. 그날 안에만 알아채면 그날치는 구제된다 — 수집이
실패한 날 저녁에 손으로 다시 돌릴 값어치가 있다는 뜻이다.

## 이 저장소가 두 번째로 배운 것

같은 모양의 사고가 이미 한 번 있었다. `| tee`가 파이썬의 종료 코드를 삼켜
승인 매수가 KIS 403으로 통째로 터졌는데 워크플로는 초록불로 끝났다
(2026-08-25 09:09). 그때 다섯 워크플로에 `set -o pipefail`을 붙였다.

**조용히 성공한 척하는 실패가 이 저장소에서 제일 비싸다.** 빨간불은 언젠가
보지만 초록불은 안 본다. 새 코드를 쓸 때마다 물어야 할 것:

> 이게 실패하면 **무엇이 빨개지나?** 아무것도 안 빨개지면 그건 실패를
> 숨기는 코드다.
