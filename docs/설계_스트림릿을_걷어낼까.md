# 스트림릿이 정말 필요한가 (2026-08-19)

물음: **깃허브 + n8n + 구글 시트/드라이브 + Apps Script만으로 안 되나?**

**답: 됩니다. 그리고 그쪽이 낫다고 봅니다.**

이 문서는 그 판단의 근거와, 무엇을 어디로 옮길지를 적는다.

---

## 1. 스트림릿이 지금 우리에게 청구하고 있는 값

### 1.1 코드

대시보드 코드 **2,757줄**. 전체 파이썬 12,367줄의 **22%**다.

### 1.2 이번 세션에서 스트림릿 때문에 한 일

기능을 늘린 게 아니라 **화면을 살려 두느라** 한 일들이다.

| 무엇 | 왜 |
|---|---|
| `NullPool`로 전환 | 30초마다 DB 파일을 갈아 끼우는데 연결이 옛 파일을 붙들어 죽음 |
| `save_and_sync` | 스트림릿이 진짜 오류를 가려서, 원인을 볼 수 있게 감쌈 |
| `ensure_schema` | 드라이브에서 받은 DB가 옛 스키마라 첫 화면이 통째로 죽음 |
| `db_guard` | 오류 하나에 화면 전체가 빨간 상자가 되는 걸 막음 |
| `화면버전` 표시 | 배포가 **18커밋** 밀려 있는 걸 알 방법이 없어서 |
| 표를 3칸으로 줄임 (2회) | 폰 폭에서 결론 칸이 잘림 |
| 전략 평가 결과에 체결가정 경고 배치 | |

**여기서 위 다섯 줄은 전부 "스트림릿 + 드라이브의 DB 파일"이라는 조합
자체가 만든 문제다.** 기능 요구가 아니었다.

### 1.3 관리해야 하는 곳

- Streamlit Cloud 계정과 앱 설정
- 거기에 넣는 Secrets (GitHub Secrets와 **같은 값을 두 군데** 관리)
- 배포 상태 (오늘 18커밋 밀려 있었고, 손으로 재시작해야 했다)

## 2. 스트림릿이 하던 일을 어디로 옮기나

| 지금 하는 일 | 옮길 곳 | 나아지나 |
|---|---|---|
| 리스크 정책 편집 | **구글 시트** | ✅ 폰에서 시트 앱이 더 편함 |
| 킬스위치 on/off | **구글 시트** 셀 하나 + Apps Script 버튼 | ✅ |
| 섹터·종목 관리 | **구글 시트** (이미 그렇게 설계함) | ✅ |
| 보유 종목 보기 | **구글 시트** (파이썬이 갱신) | ✅ 정렬·필터가 기본 제공 |
| 매매 기록 | **구글 시트** append | ✅ 검색·피벗이 공짜 |
| 실행 기록 | **구글 시트** append | ✅ |
| 전략 전략 평가 결과 | **구글 시트** | ✅ |
| 알림 | **텔레그램** | ✅ 푸시가 온다 |
| 즉석 실행("지금 돌려") | **Apps Script 버튼 → n8n 웹훅** | 같음 |
| 용어 사전 | **`docs/용어사전.md`** (이미 있음) | 같음 |
| 개발 로그(git 커밋) | **깃허브에서 직접** | ✅ |
| 다음 실행 예정 | **n8n 화면** | ✅ 진짜 스케줄이 거기 있음 |

**대체 안 되는 것이 하나도 없다.** 그리고 대부분 **더 나아진다.**

### 2.1 왜 시트가 더 나은가

- **폰에서 훨씬 편하다.** 구글 시트 앱은 정렬·필터·검색이 기본이고,
  우리가 폰 폭 CSS를 손볼 일이 없다.
- **표를 만드는 코드가 필요 없다.** 지금은 `st.dataframe` 폭 맞추고,
  칸 잘리는 걸 테스트로 고정하고 있다.
- **사람이 직접 열어서 감사할 수 있다.** 이게 원 시스템(LX MI)의 설계
  결정이기도 하다.
- **여러 기기에서 같은 것을 본다.** 스트림릿은 배포가 밀리면 다른 것을 본다.

## 3. 그러면 각 조각이 무슨 일을 하나

```
 ┌──────────────────────────────────────────────────────┐
 │  구글 시트: 사람이 보고 만지는 곳 (유일한 화면)      │
 │   · 설정: 섹터·종목·비중·리스크·킬스위치               │
 │   · 기록: 매매·실행·전망·성적                          │
 │   · Apps Script: 입력 검증, [지금 실행] 버튼          │
 └───────────▲──────────────────────────┬───────────────┘
             │ 읽기(설정)                │ 쓰기(기록)
             │                          ▼
 ┌───────────┴──────────────────────────────────────────┐
 │  GitHub Actions: 파이썬. 계산·판단·주문이 전부 여기   │
 │   · 시장/섹터 분석, 전망, 백테스트                     │
 │   · KIS 주문 (안전장치가 여기 있다)                    │
 └───────────▲──────────────────────────┬───────────────┘
             │ 부름                      │ 무거운 데이터
 ┌───────────┴───────────┐   ┌──────────▼───────────────┐
 │  n8n: 시계·연락책      │   │  DB: 30분봉·시세 캐시    │
 │   · 정시에 Actions 호출 │   │   사람이 볼 일 없는 것만  │
 │   · 텔레그램 승인 버튼  │   └──────────────────────────┘
 │   · 실패 알림           │
 └────────────────────────┘
```

**각 조각이 하나씩만 맡는다.**
- **시트** = 사람이 보는 곳
- **파이썬(Actions)** = 판단하는 곳
- **n8n** = 시각을 부르고 사람에게 말 거는 곳
- **DB** = 사람이 볼 일 없는 큰 데이터

## 4. 정직하게: 시트의 한계와 대책

### 4.1 큰 데이터는 못 넣는다

구글 시트는 **파일 하나에 1,000만 셀**까지다.

| 무엇 | 연간 줄 수 | 시트로? |
|---|---|---|
| 매매 기록 | 수백~2천 | ✅ |
| 실행 기록 | 250 | ✅ |
| 전망 기록 (섹터 8 × 매일) | 2,000 | ✅ |
| 전략 전략 평가 결과 | 30 | ✅ |
| **30분봉** | **195,000** | ❌ |
| 일봉 시세 캐시 | 15,000 | ❌ (넣을 수는 있으나 느림) |

**시세는 DB로, 사람이 읽는 것은 시트로.** 이 경계가 명확하다.

### 4.2 호출 제한

구글 시트 API는 **사용자당 1분에 60회** 정도다. 우리는 하루 8~10회
실행에 각각 몇 번씩 쓰므로 근처에도 안 간다. 다만 **한 줄씩 60번 쓰지
말고 한 번에 묶어서 쓴다**(batch append).

### 4.3 사람이 실수로 지울 수 있다

시트는 아무 셀이나 지워진다. 대책 둘.

1. **보호 범위 설정**. 파이썬이 쓰는 기록 탭은 편집 잠금
2. **파이썬 쪽 검증**. 설정을 읽을 때 형식·범위를 확인하고,
   틀리면 **매매를 중단**한다. (이미 섹터 검증기에 넣은 원칙)

### 4.4 비밀은 시트에 안 넣는다

KIS 앱키·앱시크릿·텔레그램 토큰은 **GitHub Secrets에만** 둔다.
지금도 사실상 그렇다. GitHub Secrets가 원본이고 대시보드는 그걸 다시 쓴다.
**스트림릿을 걷어내면 Secrets 관리처가 두 곳에서 한 곳으로 준다.**

### 4.5 못 하게 되는 것 하나

**즉석 대화형 계산**은 못 한다. 예: "손절선을 -3%로 바꾸면 성적이 어떻게
되나"를 슬라이더로 즉석에서.

그런데 **지금도 그걸 스트림릿에서 안 하고 있다.** 그런 실험은 전부
GitHub Actions로 실행하고 결과를 문서에 남긴다. 잃는 게 없다.

## 5. 옮기는 순서: 한 번에 지우지 않는다

**스트림릿을 당장 지우면 돌아갈 곳이 없다.** 병행하다가 걷어낸다.

| 단계 | 무엇 | 스트림릿 | 상태 |
|---|---|---|---|
| 1 | 시트에 설정 탭(섹터·종목·비중·리스크·킬스위치) 만들기 | 그대로 둠 | ✅ 2026-08-19 |
| 2 | 파이썬이 시트에서 설정을 읽게 함 (DB 설정은 백업으로 유지) | 그대로 둠 | ✅ 2026-08-19 |
| 3 | 파이썬이 기록(매매·실행·전망)을 시트에 append | **읽기 전용으로 강등** | ✅ 2026-08-19 |
| 4 | Apps Script로 검증 + [지금 실행] 버튼 | 그대로 | 안 함. 5단계가 이걸 상당 부분 대신한다 |
| 5 | 텔레그램 승인 버튼 (n8n) | 그대로 | ✅ 2026-08-23 (n8n Published, 버튼 동작 확인) |
| 6 | 2주 동안 시트만 보고 지낼 수 있는지 확인 | 그대로 | |
| 7 | **스트림릿 걷어내기** (코드 2,757줄 삭제, Cloud 앱 삭제) | 삭제 | |

### 2~3단계를 하면서 정한 것들

**킬스위치는 덮어쓰기가 아니라 AND다.** 다른 항목은 시트가 DB를 이기게
했는데, 킬스위치를 그렇게 하면 **시트가 대시보드의 킬스위치를 무력화한다.**
끄는 스위치는 어느 쪽에서 꺼도 꺼져야 하므로, 켜는 것만 양쪽 동의를 받는다.
틀리는 방향이 언제나 "안 사는 쪽"이 된다.

**시트를 못 읽으면 매매를 끈다.** 못 읽었는데 DB 값으로 그냥 돌면, 사람은
시트에서 껐다고 믿는데 코드는 켜진 채로 돈다. 이 시스템에서 제일 나쁜
고장이다.

**빈 칸의 뜻이 탭마다 반대다.** `종목` 탭에서 활성 칸이 비면 **켜짐**이고
(줄을 추가할 때마다 Y를 적게 하면 빠뜨린 종목이 조용히 사라지므로),
`설정` 탭에서 `trading_enabled`이 비면 **꺼짐**이다. 오타가 매매를 켜면
안 된다. 헷갈리기 쉬운 자리라 양쪽 코드에 왜 그런지 적어 뒀다.

**단위는 읽는 자리에서 바꾼다.** 시트에는 사람이 읽는 `15`·`-5`로 적고,
코드는 `0.15`·`-0.05`를 쓴다. 그대로 넘기면 한 종목에 자금의 1,500%다.
범위 검사도 여기서 한다. 손절선을 `5`(양수)로 적는 실수를 잡는다.

**기록 탭은 주인이 반대다.** `섹터`·`종목`·`설정`은 사람이 쓰고 코드가
읽는다. `매매기록`·`전망기록`·`일일요약`은 코드가 쓰고 사람이 읽는다.
한 탭을 양쪽이 고치면 충돌 처리를 만들어야 한다.

**재실행이 줄을 늘리지 않는다.** 줄마다 열쇠(`T31`, `F2026-08-19|반도체|20`,
`D2026-08-19`)를 붙이고 올리기 전에 시트에 있는 열쇠를 읽어 없는 것만
올린다. 워크플로 재실행은 실패를 고치는 정상적인 수단인데, 그때마다 줄이
늘면 시트를 세어 만든 숫자가 전부 틀린다.

6단계가 중요하다. **"쓸 수 있다"와 "실제로 그것만 쓰고 지냈다"는 다르다.**

## 7. 2026-08-24: 다시 물었을 때

물음이 되돌아왔다: **"MI 수집 시스템처럼 대시보드 + n8n으로 못 하나?"**

답은 5개월 전과 같다. 되고, 그쪽이 낫다. 다만 그 사이에 사정이 둘 바뀌었다.

### 7.1 5단계가 끝났다 (그리고 4단계를 상당 부분 대신한다)

텔레그램 승인 버튼이 돈다. 4단계(Apps Script [지금 실행] 버튼)를 만든
이유가 "폰에서 빠르게 누르기"였는데, **그건 텔레그램이 더 잘한다.**
시트 앱을 열어 버튼을 찾는 것보다 알림에서 바로 누르는 게 빠르다.
그래서 4단계는 건너뛴다.

남은 것은 **6단계(2주 병행)와 7단계(걷어내기)**뿐이다.

### 7.2 오늘 스트림릿에 130줄을 더했다

"지금 손익"(증권사 계좌를 조회해 평가손익을 보여 주는 구역)을 만들었다.
**걷어낼 것에 보탠 셈이다.** 정직하게 적어 둔다.

다만 그 130줄 중 화면 코드는 절반이고, 나머지(계좌 조회·값 추리기)는
어느 화면을 쓰든 필요하다. 시트로 옮기면 워크플로가 같은 값을 시트에
쓰게 되고, 정적 HTML로 가면 그 값을 JSON으로 뱉게 된다.

### 7.3 그런데 "지금 손익"만은 시트가 잘 못한다

시트로 옮기면 **워크플로가 돌 때만 갱신된다.** 하루 5번이다. 장중에
"지금 얼마야"를 열어 보면 아침 값이 그대로 있다.

이건 시트의 한계라기보다 **§4에서 적어 둔 "즉석 대화형 계산은 못 한다"의
실제 사례**다. 그때는 "지금도 안 하고 있으니 잃는 게 없다"고 적었는데,
오늘 그걸 하기 시작했으므로 그 문장은 더 이상 맞지 않는다.

선택지는 셋이고, 각각 무엇을 포기하는지가 다르다.

| 길 | 지금 손익 | 손이 가는 곳 | 포기하는 것 |
|---|---|---|---|
| **A. 시트로 끝낸다** | 워크플로 돌 때만 (하루 5번) | 시트 앱 하나 | 장중 실시간 |
| **B. 시트 + 정적 HTML 한 장** | 열 때마다 최신 | 시트 + 링크 하나 | 만드는 품 (반나절) |
| **C. 지금처럼 둔다** | 열 때마다 최신 | 스트림릿 + 시트 둘 다 | 배포 밀림·화면 죽음이 계속 |

**B를 권한다.** MI 수집 시스템이 쓰는 패턴이 정확히 이것이고(C-3),
스트림릿이 청구하던 값: 배포가 18커밋 밀리는 것, DB 파일 갈아 끼우다
연결이 죽는 것, 오류를 가려서 원인을 못 찾는 것: 이 전부 **서버가 상태를
들고 있어서** 생긴 문제다. 정적 HTML은 상태가 없어서 그 병이 원천적으로
없다.

구체적으로는 GitHub Pages에 HTML 한 장을 올리고, 그 페이지가 n8n 웹훅을
불러 계좌 값을 JSON으로 받아 그린다. n8n은 이미 돌고 있고 웹훅도 이미
쓰고 있다. 새로 만들 것은 페이지 한 장과 웹훅 하나다.

**아직 정하지 않았다.** 6단계(2주 병행)를 건너뛰고 결정할 일은 아니다.
