# LX Group MI 구조에서 무엇을 가져올까 (2026-08-19)

뉴스 수집 시스템(`LX Group MI`)의 인수인계서를 검토했다. 만족도가 높은
시스템이라니 구조가 검증됐다는 뜻이고, 실제로 재사용할 것이 여럿 있다.

**다만 뉴스와 매매는 결정적으로 다른 점이 하나 있다.**

> 뉴스는 틀려도 **안 읽으면 그만**이다. 매매는 틀리면 **돈이 나간다.**
> 그리고 주문은 되돌릴 수 없다.

그래서 "그대로 가져올 것"과 "부호를 뒤집어서 가져올 것"과 "가져오면 안
되는 것"이 갈린다. 아래는 그 분류다.

---

## A. 그대로 가져올 것

### A-1. 사람 승인 스텝: 이 문서에서 가장 값나가는 부분 ⭐

원 시스템: 텔레그램 다이제스트의 각 기사 옆에 **인라인 버튼** → 누르면
시트에 `선택여부=Y` → `/REPORT` 명령을 보내면 선택된 것만 심층 분석.

**우리 설계에는 사람이 개입할 지점이 하나도 없다.** 킬스위치뿐인데,
그건 "전부 아니면 전무"다. 그래서 지금 자동 실행을 아예 꺼 놓고 있다.

**적용안**

```
08:40  장전 분석 → 텔레그램:
       "오늘 매수 후보 4종목"
        [ ] 한화에어로 12.0%  (방산 전망 상위25%)
        [ ] HD현대일렉 8.5%
        [ ] 알테오젠 6.0%
        [ ] 두산로보틱스 4.5%
        [전부 승인] [전부 취소]

09:00  체크된 것만 시장가 매수
```

**이게 왜 큰가**: 지금 모의투자를 꺼 둔 이유가 "완전 자동이 아직 무섭다"
였다. **승인 스텝이 있으면 켤 수 있다.** 그리고 켜야 슬리피지 실측
표본이 생긴다. 지금 모든 숫자를 막고 있는 벽이 그것이다.

**주의 하나**: 승인 여부를 **반드시 기록**해야 한다. 사람이 거른 것과
시스템이 낸 것이 다르면, 나중에 성과가 전략 덕인지 사람 덕인지 알 수 없다.
`전망_기록` 테이블에 `제안=Y / 승인=Y|N` 두 칸을 따로 둔다.

### A-2. 오케스트레이터와 엔진을 나눈다

원 시스템: `LXGroup_MI`(누구를 언제 처리할지 정하는 게이트) ↔
`LXGroup_MI_Sub`(실제로 일하는 엔진). 게이트는 설정 시트를 읽어
"발송시각에 지금이 포함되나"를 보고 대상을 고른다.

**우리 것은 지금 게이트가 없다.** n8n이 그냥 정시에 부르고, 파이썬이 전부
한다. 게이트를 나누면 이런 게 가능해진다.

| 무엇 | 주기 | 왜 |
|---|---|---|
| **보유 종목 감시** (손절·목표) | 매시간 | 되돌릴 수 없는 손실을 막는 쪽이라 자주 봐야 한다 |
| **신규 후보 탐색** | 장전 1회 | 하루에 여러 번 새로 살 이유가 없다 |
| **섹터 전망 갱신** | 장전 + 12:00 | 30분봉이 쌓이기 전까지는 이 정도로 충분 |
| **일일 리포트** | 마감 후 1회 | |

원 시스템의 **"긴급 그룹은 발송시각과 무관하게 매시간"** 패턴이 정확히
여기에 맞는다. **보유 종목 = 긴급, 신규 후보 = 정기.**

### A-3. 애드혹 요청을 정식 파이프라인에 태운다 ⭐

원 시스템: "특정 키워드 검색"을 별도 코드로 만들지 않고, 임시 그룹
(`{name:'특정키워드검색', keywords:[...]}`)으로 포장해 **등록된 그룹과
완전히 같은 파이프라인**에 태운다.

**이건 편의 기능 이야기가 아니라 우리가 이미 당한 사고의 예방책이다.**

설계안 §27~28에서 찾은 것: **백테스트와 실거래가 서로 다른 일을 하고
있었다.** 백테스트는 그날 종가에 사고, 실거래는 다음 날 시가에 샀다.
그래서 5년 성적이 26~32% 부풀어 있었다.

원인은 **두 경로가 각자 코드를 갖고 있었기** 때문이다. 이 패턴을 규칙으로
세우면 그 사고가 구조적으로 안 난다.

> **규칙: 백테스트·실거래·즉석조회는 반드시 같은 함수를 탄다.**
> 다른 것은 입력(날짜, 체결 시점)뿐이어야 한다.

### A-4. 0건도 명시적으로 알린다

원 시스템: 뉴스가 없으면 무발송이 아니라 "새 기사 없음"을 보낸다.

우리도 같은 문제를 이미 겪었다. **"살 게 없었다"와 "아예 안 돌았다"가
둘 다 빈 화면**이라 원인을 못 찾았고, 그래서 실행 기록(run_log)을 만들었다.

**알림에도 같은 원칙을 적용한다.** "오늘 매수 후보 0건: 방산·반도체는
전망 하위, 나머지는 신호 없음" 처럼 **왜 없는지까지** 보낸다.

### A-5. 소스별 게이트: 섹터마다 다른 외부 지표

원 시스템: 그룹마다 어떤 수집 소스(구글/네이버/영문)를 쓸지 on/off.

우리 적용: **섹터마다 보는 외부 지표가 다르다.**

| 섹터 | 추가로 볼 것 | 확보 여부 |
|---|---|---|
| 반도체 | 필라델피아 반도체 지수(^SOX) | ✅ 8,124일 (1994~) |
| 자동차 | 달러/원 | ✅ 5,892일 |
| 2차전지 | 구리·리튬 | 구리 ✅ 6,521일 |
| 원자재 ETF | 금·은 국제 시세 | ✅ 6,516일 |
| 전 섹터 공통 | 코스피, 미 10년물 금리, 나스닥 | ✅ |

**반도체가 특히 크다.** 우리 반도체 섹터는 종목 데이터가 5년뿐인데
필라델피아 반도체 지수는 **30년**이다. 섹터 전망의 표본이 6배가 된다.

이미 카탈로그에 `전망출처` 칸을 만들어 뒀다(원자재용). 이걸 확장하면 된다.

### A-6. 하나의 표가 로그이자 상태머신

원 시스템: 기사 시트 하나가 ① 중복 판단 기준 ② 조회 대상 ③ 선택·완료
상태 저장소를 겸한다.

우리의 `전망_기록` 표가 그래야 한다.

| 칸 | 역할 |
|---|---|
| 날짜, 섹터, 지표값들 | 그날 상태 |
| 유사구간수, 중앙값, 하위10%, 상승확률 | 그날 낸 전망 |
| 제안종목 | 시스템이 제안한 것 |
| **승인여부** | 사람이 고른 것 (A-1) |
| 체결여부, 체결가 | 실제로 산 것 |
| **실제결과_20일** | **나중에 채워 넣는 칸** ← 전망이 맞았는지 |

마지막 칸이 핵심이다. **전망을 내놓고 결과를 안 남기면 전망이 쓸모없다는
것도 영영 모른다.**

## B. 부호를 뒤집어서 가져올 것

### B-1. "점수는 매기되 자동으로 걸러내지 않는다"

원 시스템의 원칙이고, 뉴스에서는 옳다. 잘못 걸러낸 비용이 "못 읽음"뿐이다.

**매매에서는 그대로 쓰면 안 된다.** 안 거르면 다 사게 되고, 그 비용은
돈이다.

**정신만 가져온다.**

> **화면과 기록에는 전부 남긴다. 주문은 좁게 낸다.**

즉 신호가 난 것은 점수와 함께 **모두 기록하고 화면에 띄우되**, 실제 주문은
엄격한 조건을 통과한 것만. 그러면 나중에 "안 산 것들이 어떻게 됐나"를
되짚을 수 있다. 우리 실행 기록(run_log)이 이미 이 방향이다.

## C. 가져오면 안 되는 것

### C-1. AI를 판단 경로에 넣는 것 ⛔

원 시스템은 Claude가 **관련성·중요도·긴급성 점수를 매기고 그걸로 거른다.**
AI가 판단의 중심에 있다.

**매매에서는 이걸 하면 안 된다.** 이유가 둘이다.

1. **백테스트가 불가능해진다.** 2021년의 어느 날에 AI가 뭐라고 했을지를
   재현할 수 없다. 그러면 5년 검증이 통째로 사라진다. 이 저장소가 지금까지
   쌓은 것이 전부 그 검증이다.
2. **같은 입력에 같은 답이 안 나온다.** 왜 샀는지를 나중에 설명할 수 없다.

**그럼 AI는 어디에 쓰나. 백테스트할 필요가 없는 곳에만.**

| 쓴다 | 안 쓴다 |
|---|---|
| 일일·주간 리포트를 사람 말로 쓰기 | 살까 말까 판단 |
| 뉴스·공시를 요약해 **참고로** 붙이기 | 종목 점수 매기기 |
| "이 종목이 왜 후보에 올랐나" 설명 | 비중 정하기 |
| 승인 화면에 배경 정보 덧붙이기 | 손절 여부 |

**규칙: 숫자를 만드는 것은 전부 파이썬. AI는 그 숫자를 말로 옮기는 데만.**

원 시스템의 **2단계 구조(1차 가벼운 스코어링 → 사람이 선택 → 2차 심층
web_search 리포트)** 자체는 훌륭하고, 우리도 **선택된 종목의 배경 조사**에
쓸 수 있다. 다만 그 결과가 매수·매도를 정하면 안 된다. **참고 자료로만.**

### C-2. 구글 시트를 데이터 저장소로 쓰는 것 (대용량)

원 문서 §8이 이미 지적한다. 우리 경우 구체적으로:

- 30분봉: 연 **19만 5천 줄**
- 전망 기록: 섹터 8개 × 매일 = 연 2천 줄 (이건 시트로도 됨)

**설정(섹터·종목·비중)은 시트, 데이터는 데이터베이스.** 이미 그렇게
설계했고, 원 문서도 같은 결론이다.

### C-3. 정적 HTML + 웹훅 프론트엔드

훌륭한 패턴이지만 **우리는 이미 Streamlit 대시보드가 있고 잘 돈다.**
폰 폭 확인까지 끝났다. 바꿀 이유가 없다.

다만 **폰에서 빠르게 눌러야 하는 것(승인 버튼)은 텔레그램이 낫다**.
그건 A-1에서 다룬다.

## D. 그래서 설계가 어떻게 바뀌나

`docs/설계_섹터기반.md`에 다음을 더한다.

| 추가 | 어디에 |
|---|---|
| **장전 후보 → 텔레그램 승인 → 09:00 주문** | §4 실행 흐름 |
| **보유 종목은 매시간(긴급), 신규 후보는 장전(정기)** | §4 실행 흐름 |
| **백테스트·실거래·즉석조회가 같은 함수를 탄다** (규칙) | §0 원칙 |
| **섹터별 외부 지표 게이트** (반도체=^SOX 등) | §3 전망 |
| **전망 기록 표에 승인여부·실제결과 칸** | §5 리뷰 |
| **0건일 때도 왜 없는지까지 알림** | §5 리뷰 |
| **AI는 설명·요약에만, 판단 경로 밖** (규칙) | §0 원칙 |

그리고 **모의투자 재개 조건이 바뀐다.** "체계를 더 갖추고"의 그 체계 중
큰 것이 **사람 승인 스텝**이었다. 그게 붙으면 켤 수 있고, 켜야
슬리피지 실측이 생긴다.
