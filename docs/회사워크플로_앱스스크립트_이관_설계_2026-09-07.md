# 회사 워크플로를 Google Apps Script로 옮기는 설계 (2026-09-07)

주인이 정한 방향은 셋이다.

1. 회사(LX) 워크플로는 자동으로 실행되지 않게 한다. 대시보드(hub.html)의 「업데이트」
   버튼을 누르면 그때 한꺼번에 수집한다. 뉴스 수집만 지금처럼 n8n에 두고 자동으로 실행한다.
2. 주식 매매는 시각을 지켜야 하므로 n8n에 그대로 둔다.
3. 회사 쪽은 뉴스 수집을 뺀 나머지를 전부 Apps Script로 옮긴다.

그리고 "내가 자격만 주고 너가 다 수행하는 형태"를 요구했다. 이 문서는 그 방식으로
옮기기 위한 설계와 절차다. **아직 아무것도 만들지 않았다.** 이 문서를 주인이 보고
방향을 확인해 주면 그때부터 만든다.

이 문서는 매매 저장소에 있지만 내용은 회사 시스템이다. 회사 코드는 `uTaxx/muwon406`에
두기로 설계했고(§7), 이 문서도 구축을 시작할 때 그쪽 `docs/`로 옮긴다.

## 0. 결론

옮길 수 있다. 사람이 할 일은 인증 세 가지뿐이고 나머지는 전부 내가 한다.

- Apps Script API 켜기(체크박스 하나).
- 주인 PC에서 `clasp login`을 한 번 실행하고, 생긴 인증 파일을 GitHub 비밀값에 붙이기.
- 스크립트를 처음 배포한 뒤 권한 허용 화면에서 「허용」을 한 번 누르기.

다만 **n8n 실행 수는 이 이관으로 크게 줄지 않는다.** 이미 2026-09-07 낮에 10분마다
돌던 수집기를 주 1회로 바꿔서 회사 쪽 예약 실행이 월 약 14,000건에서 약 240건으로
줄었다(HANDOVER.md §"계열사 수집기를 주 1회로"). 지금 남은 회사 쪽 예약 실행은 월
약 240건이고, 화면을 열 때마다 나가는 조회 웹훅 실행이 그 위에 더해진다. 이관하면 이
둘이 0이 된다. 매매 약 1,600건과 뉴스 파이프라인만 n8n에 남는다.

그래서 이 이관의 실제 이득은 실행 수보다 다음 셋이다.

- 회사 수집을 사람이 원할 때만 실행한다. 볼 것이 없는데 확인만 하고 끝나는 실행이 없어진다.
- n8n 한도를 매매가 쓴다. 뒤에 매매 워크플로가 늘어도 회사 쪽과 부딪히지 않는다.
- 구글 시트와 드라이브를 쓰는 코드가 구글 계정 안에서 실행된다. n8n의 구글 인증 정보를
  거치지 않는다.

## 2. Apps Script로 만들 수 있는지 확인한 것

Google 개발자 문서 사이트는 이 작업 환경에서 접속이 막혀 있어서 clasp 공식 저장소
문서와 여러 2차 자료로 확인했다. 확인한 출처를 §9에 적었다.

| 필요한 것 | Apps Script에서 되나 | 근거·조건 |
|---|---|---|
| 시트 읽기·쓰기, 드라이브 파일 만들기·찾기 | 된다 | `SpreadsheetApp`, `DriveApp`. 스크립트가 주인 계정으로 돌므로 별도 인증 정보가 없다. |
| DART·ECOS·FRED·관세청·KOSIS·KCCI 호출 | 된다 | `UrlFetchApp`. 하루 20,000회. 지금 하루 수십 회다. |
| xlsx 내보내기 | 된다 | 스프레드시트를 xlsx Blob으로 변환한다. |
| 화면이 부르는 HTTP 주소 | 된다 | 웹 앱으로 배포. `doGet`/`doPost`. 주소 하나에 `동작` 값으로 종류를 나눈다. |
| 브라우저에서 다른 도메인이 부르기(CORS) | 조건부 | POST 본문의 Content-Type을 `text/plain`으로 보내야 한다. 지금 hub.html은 `application/json`으로 보내는데, 그러면 브라우저가 사전 요청(OPTIONS)을 먼저 보내고 Apps Script는 그것에 답하지 못한다. hub.html의 fetch 세 곳을 고쳐야 한다. |
| 파일을 바로 내려주기 | 안 된다 | 웹 앱은 텍스트(JSON 등)만 돌려준다. xlsx는 base64로 담아 JSON으로 주고 브라우저가 파일로 저장한다(§4-4). |
| 한 번 실행 시간 | 6분 | 넘으면 강제 종료. 긴 일은 나눠서 이어 실행한다(§4-2). |
| 시간표 없이 이어 돌기 | 된다 | 스크립트가 스스로 "1초 뒤 한 번" 트리거를 등록해 다음 조각을 실행한다. 스크립트당 트리거 20개 한도가 있어 쓴 트리거는 바로 지운다. |
| 하루 트리거 총 실행 시간 | 개인 계정 90분, Workspace 6시간 | 시즌에 22개 회사 원문을 한 번에 처리하면 90분에 닿을 수 있다(§8). |
| 코드를 GitHub에서 올리기 | 된다 | `clasp push -f`, `clasp create-deployment -i <배포ID>`. 인증 파일 `~/.clasprc.json`을 GitHub 비밀값에 두고 워크플로가 다시 만든다. |
| 서비스 계정으로 올리기 | 사실상 안 된다 | clasp 문서: 서비스 계정은 스크립트를 소유할 수 없고, 공유받아야만 push할 수 있다. 사람 계정으로 로그인하는 쪽이 단계가 적다. |
| 비밀값 보관 | 필요 없다 | API 키가 이미 시트 `운영설정` 탭에 있고 스크립트가 그 시트를 읽는다. n8n과 같은 방식이다. 코드와 GitHub에는 키가 들어가지 않는다. |

## 4. 설계

### 4-1. 웹 앱 주소 하나, 동작 여섯

주소는 `https://script.google.com/macros/s/<배포ID>/exec` 하나다. 배포ID는 한 번
만들면 코드를 새로 올려도 바뀌지 않게 한다(`-i` 옵션으로 같은 배포를 갱신).

| 동작 | 방식 | 하는 일 | 응답 |
|---|---|---|---|
| `지표` | POST | 지금 `lxgroup-지표`와 같음 | 같은 JSON |
| `경쟁사` | POST | 지금 `lxgroup-경쟁사`와 같음 | 같은 JSON |
| `딜` | POST | 지금 `lxgroup-딜`과 같음 | 같은 JSON |
| `원본` | POST | 마스터 스프레드시트를 xlsx로 | `{ok, 파일이름, base64}` |
| `수집시작` | POST | 대상을 받아 작업 줄을 만들고 트리거를 등록 | `{ok, 작업ID}` 또는 이미 실행 중인 작업이 있으면 그 ID |
| `진행` | GET | 작업 한 줄의 상태 | `{상태, 단계, 진행글, 시작, 끝}` |

조회 셋의 응답 JSON은 지금 n8n 코드 노드가 만드는 것과 같은 키를 그대로 쓴다.
화면 코드를 고치는 범위를 fetch 호출 방식에 한정하기 위해서다. 옮기기 전에 같은
`code`로 n8n과 Apps Script를 둘 다 불러 JSON을 비교하는 검사를 넣는다.

코드 확인은 지금과 같다. `설정` 탭에서 `식별코드`를 찾고 `상태`가 `운영중`이어야 한다.
못 찾으면 `{ok:false, error:'등록된 식별코드가 아닙니다.'}`다. 웹 앱은 HTTP 상태
코드를 마음대로 정할 수 없어서 늘 200으로 오고, 화면은 이미 `d.ok === false`를 보고
있으므로 그대로 동작한다. `원본받기()`만 `r.ok`(HTTP 상태)를 보고 있어서 고친다.

조회 응답은 `CacheService`에 10분 캐시한다. 수집 작업이 끝나면 캐시를 지운다. 화면을
여러 사람이 여러 번 열어도 시트를 매번 다시 읽지 않는다.

### 4-2. 수집 작업. 한 줄이 한 번의 「업데이트」다

`수집작업` 탭을 새로 만든다. 칸은 작업ID, 요청시각, 요청코드, 대상, 상태, 현재단계,
진행글, 시작시각, 끝시각, 오류다. 상태는 `대기`, `진행중`, `완료`, `실패` 넷이다.

대상은 셋 중 고른다. 화면 버튼에 따라 하나만 오기도 하고 셋이 다 오기도 한다.

| 대상 | 단계 (순서대로) | 지금 n8n 워크플로 |
|---|---|---|
| 지표 | ① 지표값 수집(ECOS·FRED·관세청·KOSIS) ② 운임 수집(KCCI) ③ 지표 마스터 다시 쓰기 | 지표수집, 운임수집, 지표_마스터정리 |
| 경쟁사 | ① 공시 목록 수집 ② 원문 저장 ③ 실적 추출 ④ 비용 추출 ⑤ 부문매핑 보충 ⑥ 실적 마스터 다시 쓰기 | 공시수집, 원문저장, 실적추출, 비용추출, 부문매핑마스터, 마스터정리 |
| 딜 | ① 마지막 접수일 다음 날부터 오늘까지 DART 주요사항보고서 수집 | 딜공시수집 |

작업 실행 규칙은 이렇다.

- `작업진행()`은 트리거로만 불린다. 시작하면 먼저 자기를 부른 트리거를 지우고
  `LockService`로 잠근다. 잠금을 못 얻으면 다른 조각이 실행 중인 것이니 그냥 끝낸다.
- 한 조각은 4분 안에 끝낸다. 단계 안에서 건마다 시간을 확인하고, 4분이 지나면 지금까지
  처리한 것을 시트에 적고 1초 뒤 트리거를 다시 등록한다. 다음 조각이 이어서 처리한다.
  6분 한도를 넘어 강제 종료되면 어디까지 했는지 모르게 되므로 여유를 둔다.
- 처리 단위는 지금 n8n과 같다. 원문 저장은 원장의 `저장됨` 표시, 실적·비용 추출은
  시트에 이미 있는 (회사, 접수번호) 짝을 보고 건너뛴다. 그래서 중간에 끊겨도 다음
  조각이 같은 것을 두 번 넣지 않는다.
- 동시에 한 작업만 실행한다. 진행 중인 작업이 있는데 버튼을 다시 누르면 새 작업을 만들지
  않고 그 작업ID를 돌려준다. 화면은 그 진행을 보여 준다.
- 단계가 실패하면 그 작업을 `실패`로 적고 오류 칸에 어느 단계 어느 건에서 왜 실패했는지
  적는다. 텔레그램으로도 보낸다(§4-5). 남은 단계는 실행하지 않는다. 반쯤 된 상태로 마스터를
  다시 쓰는 것보다 멈추는 쪽이 낫다.
- 조각 사이에 시트에 진행글을 적는다. "경쟁사 ③ 실적 추출 · 22건 중 14건"처럼 쓴다.
  화면이 이 글을 그대로 보여 준다.

수집이 자동으로 실행되지 않으므로 **오랫동안 안 누르면 그만큼 비어 있다.** 딜 공시와 지표는
마지막 저장분 다음부터 오늘까지를 받으므로 구멍은 안 생기지만 한 번에 받을 양이 많아진다.
DART 목록은 한 쪽에 100건이라 한 달 밀리면 딜 공시 목록만 수십 쪽이 된다. 조각으로
나눠 실행하니 시간은 걸려도 끝난다. 화면 「업데이트」 옆에 마지막 완료 시각을 적어 두어
얼마나 지났는지 보이게 한다.

### 4-3. 화면(hub.html) 변경

- 상단 식별코드 옆에 「업데이트」 버튼과 마지막 수집 시각을 둔다. 지표·경쟁사·딜 탭의
  머리에도 그 탭만 갱신하는 작은 버튼을 둔다.
- 누르면 `수집시작`을 보내고, 받은 작업ID로 5초마다 `진행`을 물어 진행글을 버튼 옆에
  보여 준다. `완료`가 오면 그 탭의 자료를 다시 불러온다(`loadIndex(true)` 등이 이미 있다).
  `실패`가 오면 오류 칸의 글을 그대로 보여 준다.
- 화면을 닫아도 작업은 서버에서 계속 실행된다. 다시 열면 진행 중인 작업이 있는지 물어서
  이어 보여 준다.
- 주소 상수 네 개(`INDEX_URL`, `COMP_URL`, `DEAL_URL`, `원본_URL`)를 Apps Script 주소
  하나로 바꾸고 `동작`을 본문에 넣는다. fetch 세 곳의 Content-Type을 `text/plain`으로
  바꾼다. n8n 주소는 주석으로 남겨 되돌릴 수 있게 한다.
- 뉴스 관련 주소(`LOOKUP_URL` 등 10개)는 그대로 n8n이다. 건드리지 않는다.

### 4-4. 엑셀 내려받기

Apps Script 웹 앱은 파일을 그대로 돌려줄 수 없다. 두 가지 길이 있다.

1. 스크립트가 xlsx를 만들어 base64로 JSON에 담아 주고, 브라우저가 Blob으로 저장한다.
   마스터 파일은 수십 KB라 문제없다. 파일 이름은 `a[download]`로 정한다. hub.html 주석에
   "브라우저가 우리말 이름을 버리고 download로 저장하는 경우가 있다"고 적혀 있는데, 그
   경우를 위해 아스키 이름(`LX-index-master.xlsx`)을 예비로 둔다. 지금 n8n도 같은 예비
   이름을 쓴다.
2. 드라이브의 내보내기 주소(`.../export?format=xlsx`)를 돌려주고 브라우저가 그 주소로
   간다. 파일 이름은 완벽하지만 **그 파일이 내려받는 사람에게 공유돼 있어야 한다.**
   식별코드만 아는 직원은 드라이브 권한이 없을 수 있다.

1번으로 만든다. 2번은 드라이브 권한이 있는 사람만 되는 길이라 기본이 될 수 없다.

### 4-5. 실패 알림

지금은 n8n `LXGroup_실패알림`이 텔레그램으로 보낸다. Apps Script에서는 스크립트가
텔레그램 봇 API를 직접 부른다. 봇 토큰과 대화방 ID는 시트 `운영설정` 탭에 줄 두 개로
넣는다(`TELEGRAM_BOT_TOKEN`, `TELEGRAM_ADMIN_CHAT_ID`). **이 두 값은 주인이 시트에
적어야 한다.** n8n 인증 정보 안에 있는 값을 나는 읽을 수 없다.

알림을 못 보내도 작업 상태는 시트에 `실패`로 남는다. 화면이 그것을 보여 준다.
알림 실패가 작업 결과를 가리지 않게 한다.

n8n 코드 노드의 자바스크립트는 대부분 그대로 옮길 수 있다. 바뀌는 것은 넷이다.

DART 원문 조각을 시험 자료로 두고 지금 n8n이 뽑아 둔 값과 같은 값이 나오는지 본다.
시트·드라이브·UrlFetch를 쓰는 함수는 Node에서 실행할 수 없으므로 Apps Script 안에
`점검_*()` 함수를 두고 배포 뒤 내가 웹 앱을 직접 불러 확인한다.

### 4-7. 성능과 한도에서 걸리는 것

- **한 실행 6분.** n8n에서 마스터정리가 80~230초 걸렸다(HANDOVER.md). Apps Script에서
  시트 쓰기는 `setValues`로 한 번에 써야 빠르다. 셀 단위로 쓰면 수십 배 느려 6분을
  넘긴다. 회사 하나가 한 조각이 되도록 나눈다.
- **하루 트리거 총 실행 시간.** 개인 Gmail 계정은 90분, Workspace 계정은 6시간이다.
  시즌에 22개 회사 원문 22건을 받아 실적·비용을 뽑고 마스터 22개를 다시 쓰면 90분에
  닿을 수 있다. 닿으면 그날 남은 조각이 실행되지 않고 다음 날 이어진다. 작업이 `진행중`으로
  남아 있으면 화면에 "오늘 한도에 닿아 내일 이어집니다"라고 적는다.
  **주인 계정이 어느 쪽인지 확인하지 못했다.** §6에서 묻는다.
- **비용 추출.** 표를 200개까지 읽는다. Apps Script의 V8은 n8n의 Node보다 느리지 않지만
  같은 환경이 아니라 실제로 재 봐야 한다. 처음 배포 뒤 한 건 처리 시간을 시트에 남겨
  조각 크기를 정한다.
- **UrlFetch 응답 크기 50MB.** DART 원문 zip은 사업보고서라도 수 MB다. 문제없다.
- **시트 읽기.** `시장지표값` 탭이 수만 줄이어도 `getDataRange().getValues()`는 몇 초다.
  조회에 10분 캐시를 두므로 화면은 대부분 캐시를 받는다.

## 5. 옮기는 순서

한 번에 다 바꾸지 않는다. 단계마다 n8n을 켜 둔 채로 Apps Script를 먼저 세우고, 같은
결과가 나오는 것을 확인한 뒤 화면 주소를 바꾸고, 그다음에 n8n을 끈다.

| 단계 | 하는 것 | 확인 | 사람이 할 일 |
|---|---|---|---|
| 0 | 인증 준비 (§6) | GitHub Actions에서 `clasp list`가 성공 | §6의 세 가지 |
| 1 | 스크립트 프로젝트 만들기, 빈 웹 앱 배포, 배포 워크플로 | `/exec`가 `{ok:true}`를 돌려줌 | 권한 허용 「허용」 한 번 |
| 2 | 조회 4개 이식 | 같은 code로 n8n과 Apps Script 응답 JSON이 같음 | 없음 |
| 3 | hub.html 주소 바꾸기 (조회만) | 브라우저에서 세 탭과 엑셀 내려받기 확인 | muwon406 main 합치기 (§7) |
| 4 | 수집작업 틀 + 지표 대상(수집·운임·마스터) + 업데이트 버튼 | 버튼 → 진행글 → 완료 → 화면 갱신 | 없음 |
| 5 | 딜 대상 | 마지막 접수일 이후분이 들어옴 | 없음 |
| 6 | 경쟁사 대상 6단계 | 시험 자료로 추출값 일치, 마스터 파일 다시 써짐 | 없음 |
| 7 | n8n 시간표 워크플로 10개와 조회 4개를 발행 취소(unpublish) | 2주 뒤 문제 없으면 보관(archive) | 없음 |

3단계까지 되면 조회 웹훅 실행이 n8n에서 사라진다. 4~6단계에서 시간표 실행이 사라진다.
7단계 전까지 n8n 워크플로는 그대로 있으므로, 문제가 생기면 hub.html의 주소 상수만
되돌리면 된다.

6단계가 가장 크다. 실적·비용 추출 코드가 길고 회사마다 표 모양이 달라 시험 자료를
회사별로 둬야 한다. 이 단계만 다른 단계의 서너 배 걸린다.

## 6. 주인이 해야 하는 것 (인증 세 가지)

셋 다 내가 대신 못 하는 까닭이 있다. 구글 계정의 비밀값을 만드는 일이다.

1. **Apps Script API 켜기.** https://script.google.com/home/usersettings 에서
   「Google Apps Script API」를 켠다. 이것이 꺼져 있으면 clasp가 아무것도 못 한다.

2. **clasp 로그인 한 번.** 주인 PC(윈도우)에 Node.js가 있어야 한다. 없으면
   https://nodejs.org 에서 LTS를 설치한다. 그다음 명령창에서 다음을 실행한다.

       npx @google/clasp login

   브라우저가 열리고 구글 로그인과 권한 허용을 거친다. 끝나면 사용자 폴더에
   `.clasprc.json`이 생긴다(윈도우는 `C:\Users\<이름>\.clasprc.json`). 이 파일 내용
   전체를 GitHub 저장소 `uTaxx/muwon406`의 Settings → Secrets and variables → Actions
   → New repository secret에 이름 `CLASPRC_JSON`으로 넣는다.

   이 파일에는 갱신 토큰이 들어 있다. 주인 계정의 Apps Script 프로젝트를 읽고 쓸 수
   있는 값이므로 채팅이나 커밋에 붙이면 안 된다. GitHub 비밀값에만 넣는다.

   구글 계정이 둘이면 **시트와 드라이브를 가진 계정**으로 로그인해야 한다. 스크립트가
   그 계정으로 실행되면서 시트를 읽기 때문이다. 지금 n8n의 「공용 - Google Sheets」 인증
   정보가 어느 계정인지 나는 볼 수 없다. 시트 `1emQDc0-…`의 소유자 계정이다.

3. **권한 허용 한 번.** 1단계에서 내가 스크립트를 만들고 배포한 뒤, 주인이
   https://script.google.com 에서 그 프로젝트(「LXGroup MI」로 만든다)를 열어 함수
   `권한확인`을 실행한다. 권한 요청 화면에서 「허용」을 누른다. 스프레드시트, 드라이브,
   외부 접속, 트리거 넷을 처음부터 다 요청하므로 뒤에 다시 물을 일은 없다. 새 권한이
   필요해지면 그때 한 번 더 한다.

그리고 시트 `운영설정` 탭에 텔레그램 줄 두 개를 넣는다(§4-5). 이것은 인증은 아니지만
값을 나는 모른다.

계정 종류도 알려 주면 좋다. Gmail 개인 계정인지 Workspace 계정인지에 따라 하루 트리거
한도가 90분과 6시간으로 다르다(§4-7).

## 7. 코드는 어디에 두나

회사 시스템이므로 `uTaxx/muwon406`에 둔다. `apps-script/lxgroup/`과 배포 워크플로
`.github/workflows/apps-script-deploy.yml`이다. hub.html도 거기 있다.

나는 그 저장소의 `main`에 직접 올리지 못한다(허락 없이 다른 저장소의 가지에 올리지
않는 규칙이고, 실제로도 막힌다). 그래서 가지 `claude/apps-script-lxgroup`에 올리고
주인이 합친다. 합치는 것이 곧 배포다. 배포 워크플로는 `main`의 `apps-script/**`가
바뀔 때 실행되고, `workflow_dispatch`로도 실행된다.

배포 워크플로가 하는 일은 넷이다. 비밀값을 `~/.clasprc.json`으로 다시 만들고,
`npx @google/clasp push -f`로 코드를 올리고, `npx @google/clasp create-version`으로
판을 만들고, `npx @google/clasp create-deployment -i <배포ID> -V <판>`으로 같은 배포를
갱신한다. 배포ID는 처음 한 번 만들어 `.clasp.json` 옆 파일에 적어 둔다. 주소가 바뀌지
않아야 hub.html을 다시 고치지 않는다.

**muwon406은 공개 저장소다.** 코드에 키를 넣지 않는다. 스크립트 ID와 배포 ID는
공개돼도 된다. 그것만으로는 코드를 고칠 수도 실행할 수도 없고, 배포 주소는 어차피
hub.html에 적혀 나간다. `.clasprc.json`은 `.gitignore`에 넣는다. 스크립트 안의 `print`에
해당하는 `Logger.log`는 Apps Script 실행 기록에만 남고 GitHub에는 안 나오지만, 같은
규칙을 지켜 시트에서 읽은 값을 로그에 찍지 않는다.

## 8. 걸리는 것과 확인하지 못한 것

- **n8n 실행 수 절감은 월 약 240건 + 조회 횟수다.** 크게 줄이는 일은 09-07 낮에 이미
  했다. 이 이관의 이득은 §0에 적은 셋이다. 그래도 한도가 모자라면 그다음은 뉴스
  파이프라인(LXGroup_MI)이고, 그것은 이 문서 범위 밖이다.
- **주인 계정 종류를 모른다.** 개인 계정이면 하루 트리거 90분이라 시즌 첫 수집이 이틀에
  걸릴 수 있다.
- **Apps Script에서 실적·비용 추출이 얼마나 걸리는지 재 보지 않았다.** n8n 수치만
  있다(마스터정리 80~230초). 1단계 뒤 한 건을 실제로 재서 조각 크기를 정한다.
- **Google 공식 문서를 직접 읽지 못했다.** 한도 숫자(6분, 90분, 20,000회)는 2차 자료
  여러 곳이 같은 값을 적고 있어 그대로 썼다. clasp 명령과 인증 파일 위치는 clasp 공식
  저장소 문서에서 확인했다.
- **화면의 뉴스 쪽 웹훅 10개는 그대로 n8n이다.** 한 화면이 두 곳을 부르게 된다. 문제는
  아니지만 장애가 났을 때 어느 쪽인지 화면 문구로 구별되게 적어야 한다.
- **조회 웹훅이 한 달에 몇 번 불리는지 못 셌다.** 성공 실행을 저장하지 않는 설정이다.
- **자동 수집이 없어지면 화면을 안 여는 주에는 자료가 멈춘다.** 주인이 정한 방식이다.
  나중에 원하면 주 1회 자동 트리거 하나를 더하는 것은 함수 한 줄이다.
