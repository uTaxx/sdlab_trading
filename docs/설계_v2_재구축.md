## 3. 가장 큰 구조 문제: 상태를 어디에 두나

### 3.1 지금 방식과 그것이 낸 사고들

지금은 **SQLite 파일 하나(`muwon.db`)를 구글드라이브에 두고 주고받는다.**

- GitHub Actions: 실행마다 내려받고 → 일하고 → 올린다
- 대시보드: 30초마다 내려받고, 저장하면 올린다

**이 방식이 실제로 낸 사고가 둘이다.**

1. 대시보드에서 킬스위치를 켜자 `OperationalError`로 죽음. 30초 주기
   다운로드가 **파일을 통째로 갈아 끼우는데** 연결은 옛 파일을 붙들고
   있었다. (NullPool로 고침)
2. 배포된 대시보드 첫 화면이 통째로 죽음. 드라이브의 DB가 **옛 스키마**라
   `no such column: orders.reference_price`. 시작할 때 맞춰 놔도 30초 뒤에
   옛 파일로 되돌아갔다. (`ensure_schema`로 고침)

**두 사고 모두 "파일을 통째로 주고받는" 방식 자체에서 나왔다.** 고치긴 했지만
같은 종류의 사고가 또 날 구조다. 그리고 시간당 실행을 붙이면 더 잦아진다.

### 3.2 대안: 진짜 데이터베이스

| | 지금 (SQLite on Drive) | 바꾼 뒤 (호스팅 Postgres) |
|---|---|---|
| 읽기 | 파일 전체를 내려받아야 함 | 필요한 줄만 조회 |
| 동시 접근 | 나중에 올린 쪽이 덮어씀 | 데이터베이스가 처리 |
| 스키마 변경 | 파일마다 따로 맞춰야 함 | 한 곳만 바꾸면 끝 |
| 30분봉 19만 줄 | 파일이 무거워져 왕복이 느려짐 | 문제 없음 |
| n8n이 직접 읽기 | 불가능 | **가능** (알림·시트 동기화를 n8n이 맡을 수 있다) |
| 비용 | 0원 | 무료 구간으로 가능 |

**무료 선택지**: Supabase, Neon 등 Postgres 무료 구간. 우리 데이터 크기
(수십 MB 수준)는 무료 한도 안에 넉넉히 들어간다.

**이게 이번 재구축에서 얻을 수 있는 가장 큰 구조 개선이다.** 위 사고 두
종류가 통째로 사라지고, n8n이 상태를 직접 읽을 수 있게 된다.

## 4. n8n을 어디까지 쓸까. 정직한 평가

"n8n이 파이썬을 못 실행하는 게 문제라면 처음부터 다시 만들면 된다"는 지적에
대한 답이다.

### 4.1 옮길 수 있는 것과 없는 것

| 일 | n8n으로? | 왜 |
|---|---|---|
| 정시에 부르기 | ✅ **n8n이 낫다** | 클라우드 상시 가동. Actions cron보다 정확 |
| 텔레그램 알림 | ✅ n8n이 낫다 | 노드 하나면 됨 |
| 구글 시트 읽고 쓰기 | ✅ n8n이 낫다 | 노드 하나면 됨 |
| 실패 감시·재시도 | ✅ n8n이 낫다 | 이게 원래 n8n이 하는 일 |
| KIS 주문 넣기 | 🟡 가능하지만 권하지 않음 | 안전장치가 파이썬에 있다. 주문 경로가 둘이 되면 킬스위치를 우회할 수 있다 |
| **30년 지수로 유사 구간 검색** | ❌ **안 된다** | 7,300일 × 지표 6개 거리 계산. 표 계산 라이브러리(pandas/numpy)가 필요하다 |
| **백테스트** | ❌ 안 된다 | 50종목 × 5~30년을 하루씩 시뮬레이션 |
| **섹터 지수 계산** | ❌ 안 된다 | 같은 이유 |

n8n의 코드 노드에서도 파이썬이 돌긴 하지만(Pyodide), **pandas·numpy를
제대로 쓰기 어렵고 실행 시간 제한이 있다.** 위 세 가지는 그 환경에서
만들 수 없다. 만들 수 있다 해도 디버깅과 테스트가 브라우저 안에 갇힌다.

### 4.2 그래서 역할을 이렇게 나눈다

```
   n8n 클라우드                    GitHub Actions              Postgres
   ───────────                     ──────────────              ────────
   · 정시에 부르기        ──HTTP──▶ · 시장·섹터 분석    ──저장──▶  상태
   · 실패 감시·재시도               · 전망 계산                    시세
   · 텔레그램 알림        ◀──읽기───────────────────────────────  전망
   · 구글 시트 동기화                · 주문 (안전장치 여기)         기록
                                    · 백테스트
```

**규칙: 판단은 전부 파이썬에.** n8n은 시각을 부르고, 결과를 나르고,
실패를 알린다. **한 번이라도 n8n이 "살까 말까"를 판단하면 백테스트와
실거래가 어긋난다**. §27에서 이미 그 종류의 사고를 겪었다.

## 5. 확정된 섹터 (2026-08-19)

우주/항공을 방산에 합쳤다. **7개.**

| 코드 | 섹터 | 성격 |
|---|---|---|
| `ROBO` | 로봇 | 코스닥 중소형 다수 |
| `DEF` | 방산·우주항공 | 정책·지정학. KAI·한화에어로 겹침 문제 해소 |
| `SEMI` | 반도체 | 시총 상위 집중 |
| `BIO` | 바이오 | 개별 이벤트 큼 |
| `BATT` | 2차전지 | 변동성 큼 |
| `POWER` | 전력·인프라 | 전력기기 강세 |
| `AUTO` | 자동차 | 수출·환율 |

**원자재(금·은·구리)는 두 갈래로 나눠 쓴다.**
- **지표로**: 금·구리 국제 시세와 금÷구리 비율을 시장 분위기 지표에 추가.
  국제 시세라 30년치를 받을 수 있다.
- **매매 대상으로**: 관련 ETF를 종목으로 등록. 별도 섹터 `COMM`으로 둔다.

### 5.1 이 구성의 성질: 반드시 알고 가야 할 것

**7개가 전부 성장·테마·경기민감 쪽이다.** 금융·통신·유틸리티·필수소비재가
없다. 즉 **방어 섹터가 없다.**

- 나쁜 장에서 7개가 **같이** 무너진다. 섹터를 나눈 분산 효과가 작다.
- "장이 나쁘면 어디로 피하나"의 답이 **현금뿐**이다.
- 원자재 ETF(특히 금)가 유일한 도피처 후보다.

**그래서 시장 분위기 → 비중 조절이 이 설계의 핵심이 된다.** 갈 곳이
없으니 **안 사는 것으로만** 대응해야 한다.

### 5.2 종목 선정 기준

섹터에 넣을 종목은 **거래대금 최소 기준**을 넘어야 한다.

로봇·전력인프라·방산에는 코스닥 중소형주가 많은데, **거래가 적으면
슬리피지가 크다.** 그리고 우리는 슬리피지 실측이 0건이다.

**기준(초안, 대시보드에서 조절)**: 최근 20일 평균 거래대금 50억 이상.
못 넘으면 시트에 남기되 `활성 = N`.
