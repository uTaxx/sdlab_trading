# 매매 시스템을 sdlab_trading 하나로 모은다 (2026-09-07)

주인이 2026-09-07에 정했습니다. `uTaxx/muwon406`은 회사 일과 다른
프로젝트도 쓰는 저장소인데 매매 시스템이 그 안의 한 가지(`claude/reset-lfe6ro`)에
얹혀 있습니다. 매매를 `uTaxx/sdlab_trading` 하나로 완전히 옮깁니다.

## 1. 결론

바꿀 것은 셋입니다. 코드는 이 문서와 같은 커밋에 준비돼 있고, 나머지 둘은

   들어 있습니다.**
2. n8n에서 muwon406을 부르는 노드 15곳의 주소와 가지 이름을 바꿉니다.
3. muwon406에서 매매 가지와 비밀값을 정리합니다.

비밀값은 손댈 것이 없습니다. sdlab_trading에 8개가 이미 들어 있고
(2026-08-25에 검증), 2026-09-07 11:45 KST에 `운영 상태 점검`을 실행해

**GitHub 인증 키가 둘입니다.** `AutoTrading_Schedule`과 `무원406 대시보드
자료`는 "매매 - Github Actions"(`yIHNgfnxguucoU6R`)를 쓰고, `AutoTrading_Telegram`은
"Header Auth account"를 씁니다. 둘이 `sdlab_trading`에 닿는지는 **확인하지
못했습니다.** 2026-08-25 이관 문서의 4단계(기존 토큰에 sdlab_trading을
추가하는 것)가 사람 몫이었고 했다는 기록이 없습니다. Fine-grained 토큰이
muwon406 하나만 가리키면 dispatch가 404로 실패합니다. 그래서 순서의 첫
단계가 이것을 확인하는 것입니다.

## 4. 순서

**장이 닫힌 뒤에 합니다.** 평일이면 20:30~23:00 KST(20:00 리포트 뒤,
08:30 후보 산출 전), 토요일이면 09:00 전략 검증이 끝난 뒤 낮이 맞습니다.
일요일 밤은 피합니다. 월요일 00:00 종목 갱신과 08:00 기준 제안이 걸립니다.

한 단계씩 하고, 각 단계의 확인이 끝난 뒤에 다음으로 갑니다.

### 0단계. 인증 키가 닿는지 본다 (내가)

n8n `AutoTrading_Schedule`의 「기간별 전략 검증 부르기」 노드 하나만 먼저
`sdlab_trading`/`main`으로 바꾸고 그 트리거를 실행합니다. 주문이 나가지 않고
상태 DB도 안 고치는 워크플로라 시험용으로 맞습니다.

- `sdlab_trading` Actions에 `기간별 전략 검증` 실행이 새로 생기면 통과입니다.
- n8n 실행이 404나 403으로 끝나면 인증 키가 sdlab_trading에 닿지 않는
  것입니다. **사람이** github.com → Settings → Developer settings →
  Personal access tokens에서 그 토큰의 Repository access에 `sdlab_trading`을
  추가합니다. 새로 만들면 n8n 자격증명도 바꿔야 하므로 기존 토큰에 더하는
  쪽이 낫습니다.
- 텔레그램 쪽 키는 3단계 뒤에 텔레그램에서 명령 하나를 보내 `텔레그램
  n8n` 실행이 sdlab_trading에 생기는지로 확인합니다.

### 1단계. muwon406의 시간표를 먼저 멈춘다 (내가, 주인 허락 뒤)

이 커밋의 파일을 muwon406 `claude/reset-lfe6ro`에 그대로 올립니다. 두
저장소가 다시 같아지고, muwon406의 시간표 7개는 조건이 `sdlab_trading`이라
그 자리에서 건너뛰기 시작합니다. n8n이 부르는 것은 아직 muwon406에서
그대로 돕니다. **muwon406은 주인의 다른 프로젝트 저장소라 여기에 올리는
것은 주인이 허락한 뒤에 합니다.**

이 순서인 이유는 하나입니다. 2단계를 먼저 하면 두 저장소의 시간표가 몇
분이라도 같이 울립니다. 상태 DB 자물쇠(`state-write`)는 저장소 안에서만
듣기 때문에, 두 저장소가 같은 시각에 드라이브의 장부를 고치면 나중 것이
앞 것을 통째로 덮습니다.

### 2단계. 이 가지를 sdlab_trading main에 합친다 (내가)

합치면 시간표 7개가 여기서 돌기 시작합니다. 화면 배포도 같이 돕니다.

### 8-2. 저녁 확인에서 본 것 (20:22 KST)

- **n8n은 아직 막혀 있다.** `AutoTrading_Schedule`의 오늘 실행 13건(12:00부터 20:00까지)이
  전부 오류다. 그래서 오늘 15:40 분봉 수집, 17:30 체결 정산, 17:40 기록 저장,

## 9. 같은 날 발견한 것: n8n 실행 한도가 찼다

0단계에서 n8n 실행이 `Execution limit reached`로 끝났습니다. 실행 목록을
보니 `AutoTrading_Schedule`은 11:30 KST 손절 감시까지 성공하고 **12:00부터
전부 실패**입니다. 다른 워크플로도 같은 시각부터 전부 실패합니다. n8n
요금제의 월 실행 한도가 찬 것입니다.

무엇이 한도를 썼는지는 실행 목록으로 알 수 있습니다. LX 관련 워크플로
셋(`LXGroup_경쟁사_원문저장`, `LXGroup_경쟁사_실적추출`,
`LXGroup_경쟁사_비용추출`)이 **10분마다** 돌고, 하나(`LXGroup_경쟁사_마스터정리`)가
