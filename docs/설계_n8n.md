# n8n 구조 설계

*2026-08-20*

## 한 줄

**n8n은 시계와 초인종이고, GitHub Actions가 일꾼이다.**
n8n은 "지금이다"와 "누가 눌렀다"만 전하고, **무엇을 할지는 전부 저장소가
정한다.**

## 왜 n8n이 필요한가 — 두 가지, 둘 다 '늦음' 문제다

### ① GitHub cron은 몇십 분씩 늦는다

`schedule:`로 건 워크플로는 정시에 안 돈다. 부하가 몰리면 30분 넘게
밀리기도 한다.

이게 실제로 막고 있는 것:

| 하고 싶은 것 | 필요한 정확도 | GitHub cron으로 되나 |
|---|---|---|
| 장 시작 전 리포트 | 몇십 분 늦어도 됨 | ○ |
| **15:20 마감 전 청산** | 분 단위 | **✗** |
| 정규장 매시간 점검 | 몇 분 | △ |

**`workflow_dispatch`는 안 늦는다.** 불리면 바로 큐에 들어간다. 그래서
n8n이 정시에 불러 주면 15:20 청산이 가능해진다 — cron으로는 못 하던
것이고 이게 제일 크다.

### ② 버튼을 눌러도 몇십 분 뒤에 반영된다

지금은 장중 10분마다 `getUpdates`로 물어보러 간다. 거기에 cron 지연이
얹히면 **버튼을 눌러 놓고 한참 기다리게 된다.** 실제로 그랬고, 그건
"안 쓰게 되는" 이유가 된다.

n8n은 텔레그램 웹훅을 받으므로 **누르는 즉시** 안다.

## 구조

```
        ┌──────────────────── n8n (클라우드, 상시) ────────────────────┐
        │                                                              │
 시계   │  Schedule Trigger  08:40 / 09:05 / 매시간 / 15:20 / 15:40    │
        │         │                                                    │
 초인종 │  Telegram Trigger  (버튼·명령)                               │
        │         │                                                    │
        │         ├─→ [즉시] answerQuery "받았습니다"                  │
        │         │                                                    │
        │         └─→ HTTP Request ──── workflow_dispatch ─────────────┼──┐
        └──────────────────────────────────────────────────────────────┘  │
                                                                          ▼
        ┌──────────────────── GitHub Actions (일꾼) ───────────────────────┐
        │  텔레그램 (n8n이 넘겨준 것)   ← 버튼·명령 처리                   │
        │  매수 후보 제안 / 시장·섹터 리포트 / 기록을 시트로 …             │
        │         │                                                        │
        │         └─→ 구글 시트 (원본) · 텔레그램 알림 · KIS 주문           │
        └──────────────────────────────────────────────────────────────────┘
```

## 규칙 셋 — 이걸 어기면 나중에 원인을 못 찾는다

### ① n8n은 판단하지 않는다

n8n이 하는 일은 셋뿐이다.

1. 시각이 되면 부른다
2. 텔레그램에서 온 것을 받는다
3. **받은 것을 그대로 넘긴다**

무엇을 살지, 승인이 유효한지, 기준을 어떻게 바꿀지는 **전부 저장소 코드가
정한다.** 판단이 두 군데로 나뉘면 백테스트와 실거래가 또 어긋나고, "왜 그때
그렇게 됐지"를 볼 곳이 두 배가 된다.

**딱 하나 예외**: 누른 직후 "받았습니다"를 답하는 것(`answerQuery`). 이건
판단이 아니라 **인사**다. 안 하면 버튼이 도는 표시로 남아 사람이 또 누른다.

### ② 한 봇을 두 곳에서 받을 수 없다

n8n이 웹훅을 걸면 우리 쪽 `getUpdates`는 **영영 빈손**이 된다. 그리고
그 사실이 어디에도 안 나타난다 — 로그에는 "새 메시지 0개"만 남는다.

그래서 폴링 쪽(`텔레그램 명령 받기`)이 **시작할 때 웹훅을 확인하고
스스로 물러난다.**

```
■ 이 봇은 **웹훅으로 받고 있습니다**: https://…
  n8n이 받아 넘겨주는 구조입니다 — 여기서 물어보러 가면 충돌합니다.
  이 워크플로의 schedule은 꺼 두는 것이 맞습니다.
```

**n8n을 켜면 폴링 워크플로의 `schedule:`을 주석 처리한다.** 물러나긴
하지만 10분마다 헛도는 실행이 쌓이는 건 그것대로 낭비다.

### ③ n8n에 주는 GitHub 열쇠는 제일 좁은 것으로

n8n이 GitHub를 부르려면 토큰이 필요하다. 두 가지 길이 있고 **권한 차이가
크다.**

| 방식 | 필요한 권한 | 자료 크기 |
|---|---|---|
| `repository_dispatch` | **Contents: 쓰기** (= 코드를 밀어넣을 수 있음) | 자유 |
| **`workflow_dispatch`** | **Actions: 쓰기** (워크플로 실행만) | 입력 10개 |

**`workflow_dispatch`를 쓴다.** n8n이 털리면 저장소 코드까지 바뀌는 것과
워크플로가 한 번 도는 것은 전혀 다른 사고다. 자료 크기 제한은 업데이트
JSON 하나에 넉넉하다.

토큰은 **fine-grained**로, **이 저장소 하나에만**, **Actions: Read and
write** 하나만 켠다. n8n 자격증명에만 넣고 저장소에는 절대 안 올린다.

### ⚠️ 텔레그램 노드를 왜 꺼 뒀나

만들 때 **n8n이 `Telegram account_LCIP`(뉴스 시스템 봇)을 자동으로 붙였다.**
그대로 켜면 그 봇의 웹훅을 빼앗아 **뉴스 워크플로가 통째로 멈춘다.**

API로는 자격증명을 뗄 수가 없어서(반드시 어떤 것이든 가리켜야 한다)
**두 텔레그램 노드를 꺼 뒀다.** 꺼져 있으면 활성화해도 웹훅이 안 걸린다.

**켤 때 이 순서를 지킨다.**

1. 무원406 봇 토큰으로 **텔레그램 자격증명을 새로 만든다**
2. `텔레그램에서 온 것`·`받았습니다 답하기` 두 노드의 자격증명을 그것으로 바꾼다
3. 두 노드를 **켠다**
4. `텔레그램에서 온 것`의 Chat IDs에 내 chat ID를 넣는다
5. `깃허브로 넘기기`에 GitHub PAT 자격증명을 넣는다
6. 그때 워크플로를 활성화한다

**2번을 건너뛰고 3번을 하면 뉴스 시스템이 멈춘다.** 이 순서가 전부다.

### 시계 쪽은 자격증명만 넣으면 된다

텔레그램을 안 쓰므로 위험이 없다. `깃허브 PAT` 자격증명 하나를 네 노드에
넣고 활성화하면 된다. 걸어 둔 시각은 평일 08:30 / 08:40 / 09:05 / 15:40 / 17:40.

**15:20 청산은 안 걸었다** — 저장소에 그 워크플로가 아직 없다. 없는 것을
부르는 트리거를 만들어 두면 매일 실패만 쌓인다.

## 만든 것의 내용 — 워크플로 둘

### (1) 텔레그램 받기

| 노드 | 무엇 |
|---|---|
| **Telegram Trigger** (`n8n-nodes-base.telegramTrigger`) | Updates: `message`, `callback_query` **둘 다 켠다** |
| **Telegram** (`resource: callback` / `operation: answerQuery`) | 누른 즉시 "받았습니다" — 버튼이 도는 표시로 안 남게 |
| **HTTP Request** (`n8n-nodes-base.httpRequest`) | 아래 호출 |

HTTP Request 설정:

```
POST https://api.github.com/repos/uTaxx/sdlab_trading/actions/workflows/telegram-n8n.yml/dispatches

Headers
  Authorization: Bearer <PAT>
  Accept: application/vnd.github+json

Body (JSON)
{
  "ref": "main",
  "inputs": { "payload": "={{ JSON.stringify($json) }}" }
}
```

> ⚠️ `inputs`의 값은 **글자여야 한다.** 사전을 그대로 넣으면 GitHub가
> 거절한다. `JSON.stringify`가 그래서 필요하다.

### (2) 시계

**Schedule Trigger** 하나에 시각을 여러 개 걸고, 시각마다 부를 워크플로를
정한다. 전부 `workflow_dispatch`이고 몸통은 위와 같다.

| 시각(KST) | 부를 것 | 왜 이 시각인가 |
|---|---|---|
| 08:30 | `매수 후보 제안` | 09:05 매수까지 승인할 시간을 35분 준다 |
| 09:05 | `승인된 것만 매수` | 시가 근처에 산다 |
| 매시 정각 | (장중 점검 — **아직 없음**) | |
| **15:20** | (마감 전 청산 — **아직 없음**) | **cron으로는 못 하던 것** |
| 15:40 | `30분봉 수집` | 장이 끝난 뒤 |
| 17:30 | `장 마감 정산` | 그날 주문의 **최종** 체결로 기록을 바로잡는다. 17:40보다 **먼저** 돌아야 시트에 고쳐진 값이 올라간다 |
| 17:40 | `기록을 시트로` | 하루치 정리 |
| 20:00 | `시장·섹터 리포트` | 마감 4시간 반 뒤. 아래 참조 |

**리포트를 아침이 아니라 그날 저녁에 두는 이유.** 리포트의 기준은 언제나
**마지막으로 완성된 일봉**이다(`build_state`가 빈 날을 버린다). 그래서
다음 날 08:40에 봐도 내용은 전날 종가 기준이었다 — **같은 내용을 12시간
늦게 받고 있었다.** 저녁에 받으면 자기 전에 읽을 시간이 생기고, 다음 날
08:30 후보를 볼 때 이미 장 상태를 알고 본다.

**후보 제안은 같은 논리로 못 옮긴다.** 판단 근거는 똑같이 전날 종가지만,
승인 기록이 **날짜를 열쇠로** 시트에 쌓인다(`read_today(sheet_id, 오늘)`).
전날 저녁에 제안하면 그 줄이 전날 날짜로 들어가고, 다음 날 09:05 매수는
그날 날짜로 찾다가 아무것도 못 찾는다. 옮기려면 날짜 처리를 먼저 손봐야 한다.

**괄호 친 것은 아직 안 만들었다.** 승인 스텝을 켤지 정해지면 그때 만든다.

## 저장소 쪽은 준비됐다

| 무엇 | 상태 |
|---|---|
| `.github/workflows/telegram-n8n.yml` | ✅ n8n이 넘긴 것을 받아 처리 |
| `scripts/telegram_control.py --from-payload` | ✅ 물어보러 가지 않고 넘겨받은 것만 처리 |
| 폴링이 웹훅을 감지하면 물러남 | ✅ |
| n8n이 감싸 보내도(`body`) 받음 | ✅ 설정 하나 때문에 안 먹는 일을 막는다 |

**남은 것은 사람이 해야 한다** — GitHub 토큰 발급과 n8n 워크플로 두 개.
토큰 없이는 n8n이 GitHub를 부를 수 없어서 제가 대신 못 합니다.

## 켜는 순서

1. GitHub에서 fine-grained PAT 발급 (이 저장소만 · **Actions: Read and write**)
2. n8n에 자격증명으로 넣는다 (**저장소에는 안 올린다**)
3. 위 (1) 텔레그램 받기 워크플로를 만들고 **테스트 실행**으로 확인
4. 버튼을 눌러 몇 초 안에 반영되는지 본다
5. 되면 `텔레그램 명령 받기`의 `schedule:`을 주석 처리한다
6. (2) 시계 워크플로를 만든다

**3번까지는 되돌릴 수 있다.** n8n 워크플로를 끄면 웹훅이 풀리고 폴링이
다시 먹는다.

## 되돌리는 법

n8n 텔레그램 워크플로를 **비활성**으로 바꾸면 웹훅이 사라진다. 그 뒤
`텔레그램 명령 받기`의 `schedule:`을 되살리면 원래대로 돌아간다.

웹훅이 안 풀리면 손으로 지운다:

```
https://api.telegram.org/bot<봇토큰>/deleteWebhook
```

## 안 하는 것

- **n8n에서 주문을 내지 않는다.** KIS 호출은 저장소 코드만 한다.
- **n8n에 비밀값을 두지 않는다.** KIS 키·구글 키는 GitHub Secrets에만.
  n8n이 아는 것은 텔레그램 봇 토큰과 GitHub PAT뿐이다.
- **n8n에서 기준을 바꾸지 않는다.** 기준의 원본은 구글 시트다.
